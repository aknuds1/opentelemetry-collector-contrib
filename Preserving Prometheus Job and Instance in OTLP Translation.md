# Preserving Prometheus Job and Instance in OTLP Translation

## Problem Statement

Historically, OpenTelemetry specifications have treated Prometheus **job** / **instance** and OpenTelemetry **service.name** / **service.instance.id** as interchangeable representations of the same underlying identity. In practice, they serve fundamentally different purposes:
\- **Prometheus job and instance** identify the scrape configuration and target address.
\- **OpenTelemetry service.name, service.namespace, and service.instance.id** identify the logical application entity.

### Practical Issues Today

1\. **Data Loss on Scrape**: When scraping a Prometheus endpoint that exposes a target\_info metric containing service.name and service.instance.id, the scraper is currently forced to drop either the Prometheus scrape identity (job/instance) or the OpenTelemetry semantic identity (service.name/service.instance.id).
2\. **Prometheus Backend Expectations**: Users pushing OTLP to Prometheus expect to query for service.name and service.instance.id as standard resource labels, but today must explicitly configure server-side flags (e.g., keep\_identifying\_resource\_attributes=true) to prevent them from being stripped or unconditionally converted into job and instance.
3\. **Pollution of service.name in Kubernetes**: Deriving service.name directly from job often yields non-standard names (e.g., prometheus\_simple/10.42.0.15:8080), breaking correlation with pod logs and OTel SDK traces.

\---

## Requirements

1\. **Separate Storage**: Store job/instance and service.name/service.namespace/service.instance.id separately as OpenTelemetry Resource Attributes when both sets of identifiers exist.
2\. **Complete Join Key When Available**: When entity-aware synthesis is not active, if either covered-attribute translation or stored Prometheus provenance supplies a complete job/instance pair, emit one complete source verbatim; never assemble a pair from different sources. For a valid EntityRef set under the planned Prometheus mapping, synthesize one complete pair from the Resource's entity-declared identifying union instead. Preserve legacy partial or absent output when no applicable source supplies a complete pair.
3\. **Queryable Resource Attributes**: Allow users to query for service.name and service.instance.id like any other OTel resource attribute when present.
4\. **Non-Breaking Server Compatibility**: Avoid breaking changes to Prometheus Server default behavior prior to a major version bump.

\---

## Proposed Design

### 1\. Core Rules

\- **Preserve Semantic Identity**: Valid, unambiguous service.name, service.namespace, and service.instance.id from target\_info are preserved as Resource Attributes while association state is usable, and are never overwritten by scrape identity. A design with bounded cross-unit association may temporarily suppress them when it cannot prove state completeness, under that design's fail-closed contract.
\- **Defaulting service.\* from job/instance**: When service.name or service.instance.id are absent on target\_info, receivers **MAY** default them from job and instance.
\- **Opt-Out for Defaulting**: If service.name and service.instance.id are defaulted to job and instance, implementations **MUST** provide a configuration toggle allowing users to disable this behavior.
\- **Aggregated Exporter Fallback (OTLP → Prometheus)**: When exporting metrics from multiple resources, aggregated exporters look up the stored job and instance resource attributes first. If absent, they fall back to synthesizing job from \<service.namespace\>/\<service.name\> (or \<service.name\>) and instance from service.instance.id.

\---

### 2\. Prometheus Server Backwards Compatibility (honor\_labels on OTLP Endpoint)

To avoid breaking existing Prometheus Server OTLP ingestion deployments prior to a major release:

1\. **OTLP Endpoint honor\_labels Configuration**:
   \- Prometheus Server can add an honor\_labels configuration option to its **OTLP endpoint configuration**.
   \- When **honor\_labels=true**, the OTLP endpoint respects incoming job and instance resource attributes on the OTLP Resource and uses them directly as the metric's job and instance labels.
   \- When **honor\_labels=false** (default for the current major version), the OTLP endpoint preserves existing backwards-compatible behavior by deriving job and instance from service.namespace/service.name and service.instance.id.
2\. **Future Major Version Defaults**:
   \- In a future Prometheus Server major release, both honor\_labels (on the OTLP endpoint) and keep\_identifying\_resource\_attributes can switch their default setting to true.
\---

### 3\. Storing Scrape Identity: Bare (job / instance) vs. Namespaced (prometheus.job / prometheus.instance)

When preserving the original scrape identity on the OpenTelemetry Resource alongside service.\* attributes, both options ultimately translate back to job and instance labels when exported from OTLP → Prometheus.

#### Option A: Bare (job and instance) (Proposed)

\- **Resource Attributes in OTLP**: job and instance.
\- **Collector / OTTL UX**: Users writing OTTL or Collector processors can naturally inspect and modify job and instance on the OTel Resource without learning a special prefix.
\- **Consistency**: Matches how all other un-namespaced Prometheus labels (container, pod, namespace) are mapped to resource attributes without needing formal semantic convention registration.

#### Option B: Namespaced (prometheus.job and prometheus.instance)

\- **Resource Attributes in OTLP**: prometheus.job and prometheus.instance.
\- **Collector / OTTL UX**: Users modifying metrics in OTel Collector processors would need to know to target prometheus.job instead of job.

**OTLP → Prom summary**: If your OTLP data never carries **job/instance** as resource attributes (the normal, pre-PR world), nothing changes. The behavior change only kicks in when those attributes are present — which is precisely the new capability introduced by the receiver side. So in a mixed rollout, a downstream aggregating exporter that consumes post-PR receiver output will emit different **job/instance** label values than the same data emitted from a pre-PR receiver (O5–O8, O10).

### Bottom line

* **Prom → OTLP direction (default config)**: **Additive breaking** — no attribute values change, but every Resource gains **job/instance**. Consumers keying on the exact Resource attribute set may see new streams across the upgrade boundary, although the legacy Prometheus identifying triplet is unchanged.
* **Prom → OTLP direction (opt-out flag enabled)**: **Hard breaking** — **service.name/service.instance.id** can now be absent; the previous spec required them.
* **OTLP → Prom direction alone**: **No change** for pipelines that never had **job/instance** as OTLP resource attributes.
* **End-to-end (Prom → OTLP → Prom) after full rollout**: **Behavior change** — **job/instance** now round-trip verbatim rather than being reconstructed from **service.name/service.instance.id**. This is the intended fix.

There are also two subtle spec tightenings I noticed while reading: the PR explicitly excludes **job/instance** labels of **target\_info** from resource-attribute conversion (previously the "all labels" wording was ambiguous), and it explicitly handles the empty **service.name/service.instance.id** case with empty label values instead of leaving it undefined. Both close ambiguities rather than introduce new observable behavior.

## Option C: Namespaced Scrape Provenance and Identity Fallback

Option C stores complete Prometheus scrape coordinates on an eligible OTel Resource as the reserved attributes `prometheus.job` and `prometheus.instance`. They are **descriptive provenance** when no entity references them as identifying. When entity-aware synthesis is not active, a complete pair derived from the existing Resource mapping takes precedence; when that mapping supplies only part of the pair or none, the complete stored pair supplies `job` and `instance` as one fallback source. Under the planned entity-aware Prometheus mapping, a valid EntityRef set instead makes its exact identifying union authoritative and the output pair is synthesized from it. An opt-in never-derive setting stops synthesizing `service.*` from `job` and `instance`; until opted in, today's producer derivation is unchanged. The Core Contract defines eligibility, including the legacy per-series carve-out for Remote Write input without a complete pair.

Relative to the Proposed Design above, Option C changes three policy choices:

- **Never-derive becomes an opt-in setting**: A producer option stops synthesizing `service.name`, `service.namespace`, and `service.instance.id` from `job`/`instance`; the fallback keeps such targets from going jobless. Until opted in, the Core Rules' MAY-default derivation and its toggle are unchanged. Any later default flip follows the implementation's compatibility process.
- **Complete Resource-pair-first lookup without active entity synthesis**: Consumers first try to derive both `job` and `instance` from the existing Resource mapping. If that does not yield two non-empty values, they use the complete stored pair as one source; they never combine one value from each. A valid EntityRef set under the planned entity-aware mapping supersedes this legacy order and synthesizes the pair from its identifying union. This preserves OTel Resource continuity where its applicable mapping supplies the Prometheus join pair, while avoiding partial output on round-tripped Prometheus data.
- **Namespaced, descriptive storage**: `prometheus.job`/`prometheus.instance` rather than bare `job`/`instance`, carrying provenance in the name (answering the provenance objection raised against bare names in spec PR 4956), and stored as metadata rather than authority.

The Core Contract below adds the safety, lifecycle, and activation conditions needed to implement those choices. It is authoritative for Option C and supersedes conflicting Proposed Design language; the three policy differences above are not an exhaustive list of its normative constraints.

### Core Contract

Unless overridden here, the existing [Prometheus–OpenMetrics compatibility rules](https://opentelemetry.io/docs/specs/otel/compatibility/prometheus_and_openmetrics/) and the underlying exposition, OpenMetrics, Remote Write, and OTLP specifications apply.

| Term | Meaning |
| :---- | :---- |
| Producer | A Prometheus or OpenMetrics to OTLP translator that emits Option C attributes |
| Consumer | An OTLP to Prometheus translator that synthesizes `job` and `instance` labels, such as Prometheus OTLP ingestion or an aggregated Prometheus exporter |
| Reserved pair | `prometheus.job` and `prometheus.instance`, both present as non-empty strings on one Resource; descriptive provenance unless either key is referenced through an EntityRef's `id_keys`, and the output-identity fallback when entity-aware synthesis is not applied and legacy Resource translation supplies no complete pair |
| Descriptive provenance | An Option C output and contributor-proof role for non-identifying scrape coordinates. It does not by itself place either key in an EntityRef's `description_keys`; formal Entity descriptions are only the Resource keys referenced through that field |
| Normalized pair | The final `job` and `instance` label values after relabeling, target filling (filling `job`/`instance` from the scrape-target configuration), and label validation, both non-empty |
| Scrape-target identity domain | The Prometheus label space within which one normalized pair denotes one Prometheus metadata join identity. That join identity can cover one or more configured scrape loops and is not their complete internal identity. The pair-only `prometheus.scrape_target` form is a structurally encodable, pre-standardization experiment with its own pinned identity contract; it is meaningful only under explicit matching producer and consumer activation plus a single-label-space isolation guarantee. Because that hidden boundary is not self-describing in an EntityRef, the form must not escape that deployment and is not a conforming instance of a later context-inclusive convention. The interoperable standardization direction is one fixed, minimally sufficient context-inclusive identifying set whose stable, repeatable domain attributes are carried on the Resource and referenced through `id_keys`. A producer follows its pinned semantic-convention schema rather than varying `id_keys` from downstream topology; neither `schema_url` nor the Prometheus mapping version is an instance-domain discriminator |
| Legacy Resource-derived pair | Both non-empty output `job` and `instance` values produced by the consumer's existing covered-attribute mapping, without reading either reserved attribute |
| Entity-derived pair | The complete output `job` and `instance` synthesized by the planned entity-aware Prometheus mapping from the entity-declared Resource identity; reserved attributes participate only when referenced through `id_keys`, never as a verbatim fallback |
| Resource-derived pair | The complete pair from the applicable Resource mapping: the Entity-derived pair when entity-aware mapping is active for a valid EntityRef set, otherwise the Legacy Resource-derived pair |
| Covered attributes | `service.name`, `service.namespace`, and `service.instance.id` |
| Contributor | An active Resource observation that contributes to one generated `target_info` output pair; for a stateful consumer, accepted provenance evidence remains active until provably retired or its retention horizon expires; for Prometheus-to-OTLP association, an active source `target_info` series supplying metadata for one normalized pair |

An implementation does not silently discard an invalid member and synthesize identity from the remainder. | Losslessly relayed EntityRef set | A valid EntityRef set and all of its referenced Resource key/value pairs carried by a future standardized mechanism without logical alteration. A declaration that loses a referenced attribute or conflicts with producer-owned reserved attributes does not qualify |

| Entity-declared Resource identity | The intended upcoming Entity data model semantics for Resource identity assumed by Option C: exactly the union of Resource attribute key/value pairs referenced through `id_keys` across all of that Resource's entity references. | Legacy Prometheus identifying attributes | With no `entity_refs`, the present covered attributes that the Prometheus compatibility mapping treats as identifying; this mapping-specific definition does not settle OpenTelemetry's broader Resource-identity semantics |

Resource identity, the legacy Prometheus identifying subset, and Prometheus output-pair synthesis are separate decisions. Under the intended upcoming Entity data model semantics for Resource identity defined above, a valid EntityRef set supplies the entity-declared Resource identity. An entity-unaware consumer still uses today's covered mapping and gated fallback; under the planned entity-aware Prometheus mapping, that set instead supplies the Entity-derived pair and neither the legacy mapping nor the verbatim fallback overrides it. With no `entity_refs`, the covered triplet remains the identifying subset for this compatibility mapping: a complete Legacy Resource-derived pair ranks above the complete reserved pair, and partial legacy values remain identifying inputs to that legacy mapping but do not combine with reserved values in the resolved output pair. A present malformed EntityRef set is not absence: malformed EntityRefs remain governed by the Entity and OTLP specifications and do not create a new Option C fallback, permit subset synthesis, or authorize producer inference.

Option C preserves, per Option C-eligible Resource and per translation unit:

* The normalized pair exactly on each eligible emitted OTLP Resource as the reserved pair.
* When entity-aware synthesis is not applied, if legacy Resource translation supplies no complete pair, the valid reserved pair verbatim as the output `job` and `instance` labels via the fallback. Those remain the output identity labels on any generated `target_info`, but the consumed Resource attributes are not additionally projected under their reserved descriptive output names. Partial Resource attributes and any preserved EntityRefs remain metadata to an entity-unaware consumer.
* Under the planned entity-aware mapping, the Entity-derived pair rather than either verbatim source. When an entity references a reserved key through `id_keys`, the original value remains queryable through the mapping's identifying-attribute or native-metadata representation under the synthesized join key; its exact placement is still open, and its contributor evidence is entity-identifying rather than a descriptive candidate.
* The reserved pair as descriptive labels on generated `target_info` only when the consumer can prove that every active contributor to that output pair used a Resource-derived output identity and carries the same complete reserved pair as descriptive provenance. An entity-identifying or fallback-consumed contributor suppresses both descriptive labels even when its pair bytes equal every descriptive candidate; a missing, invalid, or different pair also suppresses both. Uniform all-entity-identifying and all-fallback suppression is expected and silent; mixed roles are anomalous. This rule does not change the consumer's merge, deduplication, or lifecycle behavior for any non-pair `target_info` metadata.
* When producer association state is usable, the covered attributes obtained from valid associated `target_info`, with exact presence and values, under agreement across same-pair contributors, with the covered names recognized per Covered Label Mapping — preserved without being replaced by scrape identity. Fail-closed suppression while association state is incomplete follows the producer contract below.

It does not preserve the source `target_info` series itself: sample cadence, HELP, UNIT, start timestamps, and exemplars are not represented. Sample timestamps and stale markers determine observation ordering and retirement; a stateful push producer's receiver-local association horizon additionally bounds how long accepted state remains active. Receiver-added enrichment, external labels, explicitly promoted reserved attributes, and semantics-changing processors are outside the contract.

Each consumer has one implementation-specific, default-disabled **reserved-pair semantics gate**. When disabled and entity-aware synthesis is not separately active, the two attributes are ordinary Resource metadata and all behavior is legacy. When enabled and entity-aware synthesis is not applied — either because the Resource has no EntityRefs or the consumer is entity-unaware — the gate controls atomic recognition of the complete pair, fallback when no Legacy Resource-derived pair exists, and collision-safe descriptive exposure when the Legacy Resource-derived pair wins. Entity-aware mapping is a separately versioned future capability: for a valid EntityRef set, synthesis owns the output pair and every referenced attribute follows the identifying path regardless of the reserved-pair gate. For an unreferenced reserved pair, the gate still owns reserved-name collision handling and descriptive exposure; with that gate disabled, the pair remains ordinary metadata rather than proved provenance. Producer reserved-pair emission, covered-name recovery, and future EntityRef emission have separate activation, and never-derive is a separate setting. Same-named data point attributes and labels on ordinary metric series remain ordinary labels and never form a pair. Labels on source `target_info` are metadata inputs and follow the producer association rules below.

Proof is bounded by the consumer's state model. A pull or other stateful exporter may expose provenance only with a positive finite `R` that covers every accumulated value's inactivity-retention interval, and from a consistent snapshot of the complete active contributor evidence accumulated for an exposition. A contributor may remain active indefinitely while accepted updates keep refreshing it; `R` bounds only how long an unrefreshed value can remain active. A consumer without such a bound follows the stateless-safe descriptive rule: legacy fallback output identity and Entity-derived output still work, but it omits the descriptive pair when a Resource-derived pair wins. A stateless push translator does the same because it cannot prove uniqueness across requests, even when the current request has one contributor. A stateful push translator may expose the pair only if it owns contributor retirement and uses the existing `target_info` lifecycle to determine the complete active set.

### Covered Label Mapping

Covered labels are read in two steps \- decode the wire encoding, then recognize the covered names:

* On `target_info` series, once the wire encoding is decoded, both the dotted covered names and their three underscore forms \- `service_name`, `service_namespace`, and `service_instance_id` \- are recognized, under every profile. Flattening may have happened upstream of exposition, in a producer that sanitizes attribute names at record time, and no escaping negotiation reveals that. This is a bounded exception for the three registered names on which the covered mapping depends, not a general un-escaping rule: no non-covered name is ever recovered from an underscore form. If several recognized forms of one covered name occur with the same value, they collapse to one covered attribute; if their values differ, that covered attribute is omitted with a bounded diagnostic. Recognized forms are consumed rather than retained as unrelated Resource attributes.
* Recognition applies only where Option C emission is enabled, so default translation is unaltered: The compatibility specification's default is that label keys MUST NOT be altered, so this recognition belongs to the opt-in producer behavior to be specified — but some form of it is required to preserve valid covered attributes under Section 1 when association state is usable, because escaped exposition has no dotted names to preserve without it. Where the wire carries a bare `service_name`, it rests on an assumption the wire cannot settle: That label is indistinguishable from an attribute literally so named, and no encoding reveals whether the producer flattened it at record time — `dots` and `values` settle only whether the exposition escaped it (see Pros and Cons for the cost).
* A mapping profile additionally governs the escaping schemes that encode dots recoverably. Pull paths use the negotiated Prometheus escaping scheme: `allow-utf-8` carries the dotted names directly, and `dots` and `values` have unambiguous encodings for the three covered names (under `dots`, `service.name` travels as `service_dot_name` while an attribute literally named `service_name` travels as `service__name`, since `dots` doubles underscores; under `values` the dotted name travels as `U__service_2e_name` and the legacy-valid one is not escaped at all — and each decodes to a form recognized as the covered `service.name`, the encoding's distinction being deliberately discarded per the assumption above). `underscores` needs no decoding step — its forms are recognized directly. Remote Write has no negotiation; its receiver-side profile defaults to `exact` (decode nothing) and must be set to `dots` or `values` when the upstream producer uses those encodings, or the covered attributes stay encoded and the Resource mapping supplies no legacy pair. With never-derive in effect, the reserved pair then becomes the entity-less output identity or, under future EntityRef emission, the reserved-key portion of a scrape-target entity's complete identifying set. Before standardization, that entity is emitted only under matching pinned experimental producer and consumer profiles plus an explicit isolation guarantee; under the final convention, it is emitted only with the complete context-inclusive set.
* Ordinary series labels are never decoded — only `target_info` supplies covered attributes. On `target_info`, the selected profile is decoded before names are recognized: decoded `prometheus.job` and `prometheus.instance` (for example, `prometheus_dot_job` under `dots` or `U__prometheus_2e_job` under `values`), plus the ambiguous `prometheus_job` and `prometheus_instance` forms under every profile, are removed rather than recovered. Other underscore-looking labels that are neither covered forms nor reserved aliases remain ordinary metadata (see Target metadata association).

Prometheus → OTLP decodes the selected profile, then recognizes covered names, before merging contributors. OTLP → Prometheus applies the output encoding after merging raw Resource attributes. Covered output names take precedence: a non-covered attribute that translates to the same label name is omitted with a bounded diagnostic and never overwrites or concatenates with the covered value, in place of today's joining of colliding values — reachable only where both names are emitted, under escaped output, since UTF-8-preserving output cannot collide. No profile claims general reversibility for arbitrary attribute names.

With reserved-pair semantics enabled, generated `target_info` also reserves the two final output names to which `prometheus.job` and `prometheus.instance` translate. The consumer removes the raw reserved attributes before generic Resource projection. Any other Resource attribute that maps to either reserved output name is omitted with one bounded diagnostic per affected Resource or resolved output pair and translation unit, whether the pair is exposed, consumed as fallback, invalid, conflicting, missing, or unprovable. When descriptive exposure is proved, the exact pair occupies both names; otherwise neither reserved name is emitted. The Resource attributes themselves remain intact, and explicit promotion onto ordinary metric series is unchanged. With the gate disabled, all such attributes retain legacy ordinary-metadata behavior.

### Prometheus to OTLP

A scrape producer finalizes labels under existing scrape rules (relabeling, `honor_labels` conflict handling, target filling, and label validation) and requires a normalized pair. Remote Write is broader: its protocol permits `job` and `instance` to be absent independently. Option C therefore applies per series only when both labels are present with non-empty values. A valid Remote Write series missing either label stays entirely on its legacy translation path, including today's partial covered-attribute derivation, grouping, and `target_info` association; it emits no reserved pair or inferred EntityRefs and receives no Option C completeness diagnostic or guarantee. Complete siblings in the same request still use Option C. This carve-out covers absent labels only; present empty values remain governed by Remote Write validation and existing receiver behavior and never form a complete pair.

For an eligible series, the producer groups ordinary points by the exact normalized pair and associates `target_info`. The pair is stored once per Resource as the reserved attributes; `job` and `instance` are not repeated as point attributes. Covered-attribute assignment then follows the target-metadata state:

* **Covered-present target** — valid covered attributes obtained from associated `target_info`: The translation policy preserves them as inputs to the covered mapping and the pair remains descriptive. With no `entity_refs`, those attributes enter the legacy Prometheus identifying subset. When underscore aliases are recovered, the result is an opt-in compatibility interpretation of a lossy wire form, not proof of application authorship and not an entity declaration.
* **Covered-absent target** — no valid covered attributes: With never-derive opted in, covered attributes stay absent and the pair is available to the consumer fallback; with derivation on (the default), covered attributes are derived as today, enter the entity-less legacy identifying subset, and leave the fallback dormant.

Future EntityRef emission is ordered after the Resource attributes and entity-less resolver above are known:

* Relay a losslessly relayed EntityRef set when a standardized relay mechanism exists; do not reconstruct or augment it. Exactness is logical rather than byte-for-byte: the mechanism may re-encode the data, but it preserves the complete set and every referenced Resource key/value pair. Today's flattened Prometheus formats do not provide that mechanism. A present declaration that is malformed, loses a referenced attribute, or conflicts with the producer-owned normalized pair is not silently repaired, rebound to the pair, or treated as absence; those conflict rules remain standardization work.
* Only when no source EntityRef declaration is present, emit an inferred application EntityRef set if accepted values supply every identifying key required for every emitted entity under the producer's pinned semantic-convention schema and the receiver can reliably assert every value. Populate each EntityRef's `schema_url` when that schema defines one; otherwise leave the permitted field empty. Covered-name recovery may supply values under Option C, but that lossy compatibility interpretation is neither proof of application authorship nor authority to emit a partial entity.
* If the entity-less resolver would consume a complete reserved pair because the Legacy Resource-derived pair is incomplete, the entity-era counterpart is the sole working-name `prometheus.scrape_target` EntityRef with every identifying key defined for that entity type. It denotes the Prometheus metadata join identity, not the complete identity of a configured scrape loop. The pair-only form `{type: prometheus.scrape_target, id_keys: [prometheus.job, prometheus.instance]}` is a structurally encodable, pre-standardization experiment with its own pinned identity contract. It applies only under explicit matching producer and consumer activation plus a single-label-space isolation guarantee that prevents independent domains from being combined; it must not escape that deployment and is not a conforming instance of the final entity convention. The final interoperable semantic convention instead defines one fixed, minimally sufficient context-inclusive identity whose stable, repeatable domain attributes are carried on the Resource and referenced through `id_keys`. If the producer cannot reliably supply that complete set, remain entity-less and keep the reserved-pair fallback rather than emit an incomplete entity. Partial covered attributes remain unreferenced, non-identifying Resource metadata; they become formal Entity descriptions only if an EntityRef names them in `description_keys`. Do not infer this entity alongside an application EntityRef set: all referenced key/value pairs would enter the identifying union and make application identity depend on scrape configuration.
* Covered attributes derived only from the normalized pair under today's defaulting create no EntityRef, so default derivation remains on the entity-less legacy path. If neither a complete reliable application EntityRef set nor the scrape-target fallback case applies, remain entity-less rather than emit an invalid or misleading entity.

| Scenario | Behavior |
| :---- | :---- |
| Complete pair; no target metadata | Store the reserved pair; with never-derive opted in, leave covered attributes absent (output-identity fallback); otherwise derive them as today |
| Complete pair; valid, agreeing active `target_info` | Store the reserved pair descriptively; preserve the merged covered attributes as covered-mapping inputs and, without `entity_refs`, as legacy Prometheus identifying attributes; consume the source series |
| Future EntityRef emission; losslessly relayed EntityRefs | Preserve their complete logical declaration; the planned consumer synthesizes from their identifying union and the producer adds no inferred entity |
| Future EntityRef emission; present invalid or conflicting declaration | Do not repair it, synthesize from a subset, rebind referenced reserved keys, or treat it as absent; follow the Entity, OTLP, and future relay specifications |
| Future EntityRef emission; no source EntityRefs; reliable complete application identity | Add the complete EntityRef set selected by the pinned inference policy and schema; keep the reserved pair descriptive |
| Future EntityRef emission; entity-less resolver would consume the complete reserved pair | Add only `prometheus.scrape_target` with the full identifying set defined for that join-identity entity type. The pair-only form is a pre-standardization experiment requiring a matching pinned producer/consumer profile and an explicit isolated-domain guarantee; it is neither generally interoperable nor conforming under the final convention. Under the final context-inclusive definition, missing required domain attributes leave the Resource entity-less with the reserved fallback. Retain partial covered attributes as unreferenced, non-identifying Resource metadata unless an EntityRef explicitly names them in `description_keys` |
| Cross-request association state tainted | Store the reserved pair; consume and rebuild from `target_info` but suppress all of its Resource metadata, then apply the no-target-metadata covered-attribute behavior until recovery |

| `target_info` labels named `prometheus.job`/`prometheus.instance`, their underscore forms, or profile-encoded forms that decode to them | Decode the selected profile, then drop them; the pair is taken from the scrape, never read from target metadata, so they cannot overwrite it |
| Scrape identity incomplete after target filling | Fail that series with one bounded diagnostic; emit no partial pair |
| Valid Remote Write series missing `job`, `instance`, or both | Preserve legacy translation for that series; emit no reserved pair or inferred EntityRefs and make no Option C completeness diagnostic; complete siblings remain eligible |
| Invalid or conflicting `target_info` | Exclude the invalid series or conflicting key with one bounded diagnostic; valid siblings continue |
| `target_info` whose pair matches no ordinary series in the unit | Consume it without output; a stateful push producer may retain its accepted state for a later request only under the cross-request horizon and recovery contract below |

#### Target metadata association

Classification uses the final relabeled name. A series named exactly `target_info`, with Gauge, Info, unknown, or no type — for Remote Write 2.0, with Gauge, Info, or unset metadata — is a target-metadata candidate. At its selected greatest timestamp, scalar observations may be usable and any native-histogram observation is invalid target metadata. Any selected observation under another metric type is invalid regardless of shape. Suffix-looking names such as `target_info_total` stay ordinary metrics, and type suffixes are never stripped.

Within one translation unit:

* Identify each source series by its exact complete final label set; a hash may index candidates but cannot establish equality. An observation is either a scalar sample or a native-histogram datum. Select the greatest timestamp across both shapes and ignore lower-timestamp observations. With no observations, make no state change. At the selected timestamp, any histogram makes the series invalid. Otherwise, all scalar samples being stale retires it, all being non-stale with value `1` activates it, and every other mixture or value makes it invalid. An unsupported metric type makes any selected observation invalid regardless of shape.
* Determine all target-metadata state changes before associating ordinary series, so request order cannot change the result. Association is a snapshot operation, not a point-by-point temporal join.
* Decode the selected wire profile first. Then remove the metric name, the `job` and `instance` identity labels, decoded `prometheus.job` and `prometheus.instance`, and the `prometheus_job` and `prometheus_instance` forms recognized under every profile. Recognize covered names in the remaining labels per Covered Label Mapping — the three covered underscore forms regardless of profile, encoded dots per the selected profile.
* For a covered key, retain it only if every active contributor supplies the same non-empty string value, or every contributor omits it. A presence, type, empty-value, or value disagreement omits that key.
* For other metadata, retain a final Resource key only if every active contributor supplies the same value. Presence, value, type, or translated-name disagreement omits that key. Unambiguous keys continue.

Scrape association never crosses translation units. A push producer may carry association across requests only when it owns a positive association horizon `H` and can require every active source `target_info` series to deliver an accepted state transition not already represented by retained state within every `H`. `H` MUST cover the maximum scrape or emission interval plus delivery, retry, replay, and out-of-order delay. Without that contract, the producer remains request-local. Cross-request state is scoped per receiver instance and, where applicable, tenant, and keyed by the exact normalized pair and exact complete final label set; hashes may index buckets but cannot establish either equality.

For each contributor, retain the selected source timestamp, the receiver-local time of its last accepted state transition not already represented by retained state, and one of three states: active with metadata after profile decoding and key-local validation, retired by a stale marker, or invalid-series. Retired and invalid-series states contribute no metadata. A greater source timestamp replaces the stored state and a lower timestamp is ignored. At an equal timestamp, active plus active remains active, retired plus retired remains retired, and every other combination is invalid-series; invalid-series is absorbing at that timestamp. A greater-timestamp transition, or an equal-timestamp transition into the stricter invalid-series state, refreshes receiver-local retention time; an exact equal replay and every lower-timestamp observation do not. A catch-up input strictly after a restored checkpoint position is eligible for reconciliation exactly once, but its source position does not make its observations new state transitions: the timestamp and state rules above still determine whether they change state or refresh retention. Receiver-local elapsed time, never the source timestamp, drives expiration. These rules make reconciliation commutative across requests and prevent future-dated samples or repeated retries from extending retention indefinitely.

A newer invalid-series observation tombstones that contributor's previous active metadata until a greater-timestamp valid observation supersedes it or the tombstone expires. Per-series decoding conflicts and cross-contributor agreement conflicts instead omit only the affected key; they do not turn otherwise valid series into invalid-series states or remove other unambiguous metadata, and valid siblings continue. Diagnose an invalid observation or conflicting key only when processing the affected translation unit, not whenever retained state is reused. Expire active, retired, and invalid-series records only once elapsed receiver-local time since the last accepted transition is greater than `H`. Horizon expiry is normal retirement under the refresh precondition, not capacity eviction, and does not taint the scope.

A target-info-only request may commit observations accepted for association state, including stale and invalid-series observations, even though it produces no OTLP metrics. Validate one translation unit into a staged delta, then reconcile comparison, capacity, taint, association output, and publication against one consistent prospective snapshot. A rejected translation changes neither association state nor taint; a later downstream-consumer failure does not roll back accepted state, because delivery remains outside this contract. Atomic reconciliation prevents concurrent requests from regressing timestamps or clearing a newer taint.

Both pair entries and their contained contributor states are bounded. Cross-request mode starts the whole association-state scope tainted unless a continuity-qualified restore supplies eligible untainted state; a successful restore carrying taint starts with that restored taint instead of adding a new startup loss. Its atomic checkpoint contains complete canonical raw association entries, never materialized enriched Resources. Each entry binds the exact normalized pair and exact complete final contributor label set to the selected source timestamp, active, retired, or invalid-series state, decoded and key-locally validated active metadata, and receiver-local age since the last accepted transition. Scope state includes an explicit taint state, a monotonically advancing loss generation, the receiver-local age since the most recent loss, diagnostic anomaly state and cadence age, `H`, capacity, and the logical association-state scope identity. A versioned compatibility fingerprint covers the producer state schema, pair normalization and pair and contributor key schemas, observation selection, classification, and validation semantics, mapping profile, covered-name recognition mode, and — when EntityRef emission is active — the entity-emission policy and applicable entity semantic-convention schema version; independent output policy such as `never-derive` is not part of that fingerprint unless it changes the entity-emission decision. The checkpoint also binds the source cursor schema and every partition's identity and exact inclusive position, and the state represents exactly the inclusive input prefix through those positions. All receiver-local ages advance through downtime. Before eligibility, expired contributors and restored taint are evaluated with one clock and the same strict greater-than-`H` boundary; an unchanged diagnostic may repeat only when its restored cadence age is at least `H`. A durable source replays from each exclusive successor through a captured startup watermark; a boundary observation already represented by the checkpoint neither changes state nor refreshes retention. Association-derived metadata remains disabled throughout catch-up regardless of restored taint. Replayed units otherwise follow the protocol's existing delivery semantics: any ordinary translated output remains available, every Option C-eligible emitted Resource carries the reserved pair and any EntityRefs required by the active producer policy, and an accepted target-info-only unit commits association state without emitting output. The switch that enables eligible metadata and live input is atomic and fenced so input can neither bypass catch-up nor be applied twice. Catch-up suppression itself is expected and does not create a loss transition. A no-gap handoff instead fences the old owner at an exact cutover position, transfers state and positions atomically, and starts the new owner strictly after that position. Any missing canonical field or source position, incompatible fingerprint, gap, overlap without safe deduplication, state-position skew, replay failure, or inability to retain restored or replayed state makes the restore fail and discards the partial restore. Implementations without one of those continuity mechanisms always warm after restart.

Capacity eviction, overflow, or inability to retain an accepted observation discards the whole affected pair entry and atomically sets or extends the scope-wide taint. The translation unit whose accepted delta triggers the loss is tainted too, including during restore catch-up. While tainted, the producer continues rebuilding raw contributor state but suppresses all current and cached `target_info`-derived covered and non-pair Resource metadata for every pair in the scope; it cannot fall back to request-local association while the cross-request active set is incomplete. Resource classification proceeds without association-derived attributes, so existing derivation or never-derive behavior still applies, and every Option C-eligible emitted Resource still carries the normalized pair as the reserved pair. Materialized enriched Resource snapshots are not association state and must never leak metadata during taint.

Clear the taint only once elapsed receiver-local time since the most recent loss is greater than `H`, with no accepted observation discarded during that interval; every further loss atomically extends the deadline. Contributor expiry and taint recovery use the same clock and strict boundary in one reconciliation, so no state that should still be active at exactly `H` is omitted from the recovery decision. A continuity-qualified restore avoids adding a new startup loss but preserves any restored taint and its downtime-adjusted deadline. Capacity-driven loss and a supplied restore that is corrupt, incompatible, incomplete, or loses continuity are anomalous and emit one association-state diagnostic on transition. Additional losses while already tainted do not create new transitions, and the diagnostic may repeat at most once per `H`. An implementation that intentionally has no restore facility performs expected, silent startup warm-up. Recovery can change a target from covered-absent or scrape-derived covered state to `target_info`-derived covered state. Without `entity_refs`, that changes the legacy Prometheus identifying subset; it can also re-key downstream Resource grouping and Prometheus series.

If a changed label set is not accompanied by a stale marker for the old series, both remain active until stale retirement or association-horizon expiration. Their metadata is merged under the agreement rules above; the translator does not silently treat the new series as a per-key replacement. Remote Write delivery, partial-write accounting, cross-request output ordering, and exactly-once semantics remain governed by the protocol and receiver.

### OTLP to Prometheus

The consumer resolves one output identity per Resource and uses that same result for ordinary metric labels, accumulator signatures, generated-`target_info` grouping, and output. When planned entity-aware mapping is active for a valid EntityRef set, the Entity-derived pair wins and no verbatim source overrides it. Otherwise, with the reserved-pair semantics gate disabled, both reserved attributes are ordinary Resource metadata and the consumer uses legacy covered translation. With the gate enabled, a complete Legacy Resource-derived pair wins; otherwise a valid reserved pair supplies both labels verbatim. If neither legacy-resolution source is complete, the consumer preserves today's partial or absent output; an ordinary absence is not diagnostic, while an invalid reserved pair is.

| Scenario | Behavior |
| :---- | :---- |
| Entity-aware mapping active; valid EntityRef set | Use the Entity-derived pair synthesized from the complete identifying union. If either reserved key is referenced through `id_keys`, record entity-identifying evidence and leave its value placement to the entity mapping regardless of the reserved-pair gate. If neither is referenced, the pair is a descriptive candidate only with the gate enabled and otherwise remains ordinary metadata |
| Entity-aware mapping inactive for a valid EntityRef set, or Resource has no EntityRefs; gate disabled | Unchanged legacy covered translation; the pair is ordinary Resource metadata |
| Entity-aware mapping inactive for a valid EntityRef set, or Resource has no EntityRefs; gate enabled; complete Legacy Resource-derived pair | Use the Legacy Resource-derived pair. A valid reserved pair is a descriptive candidate only when neither key is referenced through `id_keys`; otherwise record entity-identifying evidence even though synthesis is inactive |
| Entity-aware mapping inactive for a valid EntityRef set, or Resource has no EntityRefs; gate enabled; partial or absent Legacy Resource-derived pair; valid reserved pair | Fallback: use the complete reserved pair verbatim. Record entity-identifying evidence if either key is referenced through `id_keys`, otherwise fallback-consumed evidence; retain partial Resource attributes and any EntityRefs as metadata. Generated `target_info` still uses the resolved pair as its `job`/`instance` identity, but does not expose the consumed Resource attributes under their reserved descriptive output names |
| Entity-aware mapping inactive for a valid EntityRef set, or Resource has no EntityRefs; gate enabled; partial or absent Legacy Resource-derived pair; no reserved pair | Preserve legacy partial or absent `job`/`instance` output without a new diagnostic |
| Entity-aware mapping inactive for a valid EntityRef set, or Resource has no EntityRefs; gate enabled; any legacy mapping; one reserved attribute present, or either value empty or non-string | Ignore the invalid pair for output identity with one bounded diagnostic; preserve legacy Resource-derived output and retain the attributes on the Resource, but do not project them under reserved `target_info` names while the gate is enabled |
| Invalid EntityRef set | Follow Entity and OTLP validation behavior for the payload as a whole; do not discard invalid members and do not enter a new Option C fallback because validation failed |
| Point attributes named `prometheus.job` or `prometheus.instance` | Ordinary translated labels; the fallback never reads them |
| Reserved attribute explicitly promoted (`promote_resource_attributes`, or `promote_all_resource_attributes` minus `ignore_resource_attributes`) | Emit it under its translated name on ordinary series; output-identity handling is unchanged |
| Same-pair fan-in among fallback Resources | Keep existing generated-`target_info` grouping and non-pair metadata behavior; the consumed pair is not emitted descriptively, and this expected suppression is silent |
| All contributors are entity-identifying | Suppress both descriptive labels; the reserved values belong to the identifying-attribute path, so this is expected and silent |
| Descriptive, entity-identifying, or fallback contributors converge on one output pair | Suppress both descriptive labels even when every reserved-pair value is byte-identical; mixed roles follow the proof-state diagnostic cadence |
| Several Resource-derived contributors produce one output pair | Emit both descriptive pair labels only if every active contributor is a descriptive candidate with the same complete pair; otherwise omit both and follow the proof-state diagnostic rules below |
| `target_info` generation disabled or renamed | The setting remains authoritative |

The proof rule is intentionally stricter than agreement within the current request. A pull exporter must evaluate a consistent snapshot of evidence recorded before any last-value accumulator overwrite. A stateless push translator always omits the descriptive pair when a Resource-derived pair wins because a later or earlier request may contain another contributor. A stateful push translator may expose it only if it owns contributor retirement and evaluates the complete active set through the existing `target_info` lifecycle. Entity-identifying evidence participates as a suppressing role and never qualifies as descriptive provenance. No Option C rule merges additional non-pair Resource attributes or redesigns existing `target_info` grouping.

For example, two Prometheus servers may scrape one application Resource with legacy identifying attributes `service.name="api"` and `service.instance.id="i-1"`, while storing pairs `("prometheus-a", "10.0.0.8:8080")` and `("prometheus-b", "10.0.0.8:8080")`. Both Resources translate to the same output `job="api", instance="i-1"`, and identical metric data may also collide under today's accumulator signature. Contributor evidence is therefore retained before that overwrite. The consumer preserves the Resource-derived output join and suppresses both provenance labels on the shared `target_info`; it does not select the surviving accumulator value or concatenate the origins. A changed, missing, or stale provenance state continues to suppress until it is provably retired or ages out. This is Option C's explicit tradeoff: join correctness and covered-mapping precedence take priority over representing several scrape origins on one info series.

Byte agreement alone is insufficient. If one contributor derives output `("api", "i-1")` from its Resource and carries that same reserved pair descriptively, while another contributor with no complete Resource mapping consumes reserved pair `("api", "i-1")` as fallback, both resolve to the same output pair but have different roles. The consumer suppresses the descriptive labels because exposing them would present the fallback contributor's output-identity input as descriptive provenance.

The same rule covers EntityRefs. If either reserved key is referenced through `id_keys`, the pair is entity-identifying even when its bytes happen to match a descriptive candidate on another contributor. Uniform entity-identifying suppression is expected; convergence with a descriptive or fallback role is anomalous because one output pair is aggregating different identity functions.

For a stateful consumer with a positive finite `R` that covers every accumulated value's inactivity-retention interval, the proof state follows these rules:

* Record evidence for every data point accepted for accumulation, after validation and ordering acceptance are determined but before last-value reduction, grouped by its exact resolved output labels and Consumer series key. The key uses the same field and value normalization intentionally used by accumulation, but encodes presence, collection, and field boundaries injectively; concatenation with an in-band delimiter cannot establish equality. A hash or serialized signature may select a bucket only when the complete structural key is then compared. Retain the contributor's output-identity role as part of the state: descriptive candidate with its exact complete pair, entity-identifying, fallback-consumed, missing, or invalid.
* Repeated evidence for the same Consumer series key and provenance state refreshes that state. A different state coexists; it never replaces earlier evidence merely because it arrived later. An input position already represented by a restored checkpoint neither refreshes evidence nor changes accumulated values. An input at a later position is eligible for ordinary accumulator processing exactly once; only an accepted recorded-value observation refreshes evidence, and source position alone does not override timestamp, no-recorded-value, or validation rules.
* A stale or no-recorded-value observation stops refreshing matching evidence, but removes it immediately only when the consumer has a separate stable contributor identity and can prove that the last contributor represented by that exact evidence retired. A shared Consumer series key is not such proof for truly indistinguishable contributors, so their matching evidence remains through exactly `R` and expires only when its age is greater than `R`. Distinct complete keys that collide in an index remain separate; retiring one never changes the other's evidence. This may conservatively suppress provenance for more than `R` after a conflict ends, until the first snapshot after the strict boundary.
* Proof and diagnostic state are bounded. When an observation cannot be retained, set one overflow taint for the entire proof-state scope and refresh it on every discarded observation. While tainted, suppress descriptive provenance for every output pair in that scope until elapsed time since the last discard is greater than `R`. Eviction must never turn disagreement into apparent agreement, and overflow must not require an unbounded set of per-pair taints.
* After startup or loss of proof state, suppress descriptive provenance through exactly `R`; stateful exposure becomes eligible only once the loss-free interval is greater than `R`. A continuity-qualified restore may avoid a new cold-start interval only when its atomic checkpoint binds complete canonical accumulated entries — metric metadata and data points, Resource attributes and EntityRefs, scope name, version, schema URL and attributes, and the receiver-local age since each value's last accepted update — together with contributor evidence and ages, overflow-taint epoch and age, diagnostic state and cadence age, a compatible resolver, reserved-pair gate, entity-aware mode and synthesis version, output mapping, Consumer series-key schema, `R`, and capacity to the exact source position for every partition in the proof-state scope. Downtime advances all ages. State older than its strict retention boundary is pruned atomically before eligibility, and restored taint remains authoritative. Missing or incompatible canonical fields make the restore incomplete; exact-key indexes are rebuilt from the canonical entries before restored state can become eligible.
* Restore catch-up starts at each checkpoint position's exclusive successor and continues through a captured startup watermark. Inputs already represented by the checkpoint are ignored for state and accumulation; source-position deduplication applies each later position at most once. Any gap, overlap without safe deduplication, state-position skew, missing position, replay failure, or partial application discards the partial restore and enters normal warm-up. A no-gap handoff instead uses the fenced ownership rule in the Continuity-qualified restore definition. Current Collector consumer paths have neither mechanism, so they always warm after process restart. An implementation intentionally lacking restore performs silent expected warm-up; a supplied restore that is corrupt, incompatible, incomplete, or loses continuity is a scope anomaly and emits one proof-state diagnostic on transition.
* During catch-up, any exposition uses one consistent catch-up snapshot. Ordinary accumulated metrics and fallback or Entity-derived output identity remain available as applicable, but descriptive provenance stays suppressed until replay reaches the watermark and the transition to live input is atomic. Catch-up suppression itself is expected and does not create a proof anomaly. This state-continuity rule does not add an exactly-once transaction with downstream delivery.
* For each exposition, use one receiver-local clock reading to prune accumulated values and evidence whose ages are greater than their retention horizons, determine startup and overflow recovery, and snapshot accumulated values, Resource attributes and EntityRefs, scope name, version, schema URL and attributes, value-update ages, proof evidence, diagnostic state, and the scope-wide overflow epoch. Evaluate proof before existing first-wins non-pair metadata reduction. Concurrent accumulation may become visible entirely before or entirely after that snapshot, never as values without their evidence or evidence without its value, Resource, EntityRefs, and scope state. In particular, an untracked value cannot survive the snapshot that clears the taint caused by losing its evidence.
* All-missing evidence, all-fallback evidence, all-entity-identifying evidence, stateless inability to prove, and startup warm-up are expected and produce no proof-state diagnostic. Retaining old evidence until expiration does not itself create a new anomaly transition. Mixed presence, different complete pairs, mixed descriptive, entity-identifying, and fallback roles, invalid evidence, and overflow are anomalous. A stateful consumer emits one proof-state diagnostic on entry to a distinct anomaly and may repeat it no more than once per `R` while that anomaly remains unchanged. An invalid pair may also produce its input-local bounded diagnostic when observed, but the implementation coalesces both causes within one translation unit and exposition does not re-log the retained invalid state.

Output rules:

* Generated `target_info` follows existing conventions — a value-`1` `target_info` Gauge, or OpenMetrics `target` Info where that representation is preserved — never both. Sample scheduling is unchanged: ingestion interpolation, Remote Write timestamp selection, and timestamp-less pull exposition keep existing behavior.
* Collisions with a real metric named `target_info` follow existing behavior. PromQL matches the concrete `target_info` name, not the OpenMetrics family name `target`.
* Exact round-tripping of non-covered dotted attribute names requires a UTF-8-preserving translation strategy; the covered names survive underscore exposition through recognition.

### Entity Data Model

The OpenTelemetry Entity data model and the protocol's `Resource.entity_refs` field are both at Development maturity. This section records the planned Prometheus OTLP endpoint direction and the intended upcoming Entity data model semantics for Resource identity assumed by Option C, rather than current published behavior: for a Resource with a valid EntityRef set, the identifying input is exactly the union of Resource attribute key/value pairs referenced through `id_keys` across all of that Resource's EntityRefs, and planned ingestion synthesizes `instance` as a UUIDv5 of that union. The mapper consumes the exact referenced union present in its input after any upstream processing; it does not implicitly apply schema conversion or add Entity type, `schema_url`, EntityRef decomposition, or downstream topology to the UUID input. Ref ordering, `id_keys` ordering, and the decomposition of an identical referenced key/value union across EntityRefs therefore do not change that input. This is Prometheus synthesis equivalence, not a claim that differently typed, versioned, or decomposed EntityRef declarations are merge- or relay-equivalent: type, `schema_url`, key roles, and set membership remain part of Entity validation and compatibility. An upstream schema conversion must update the Resource attributes and their references together; synthesis then consumes the resulting union, which may re-key output. The exact `job` rule, UUID canonicalization/version details, and placement of identifying attributes in Prometheus remain part of that planned mapping. No verbatim pair carve-out applies once EntityRefs govern.

| Payload and consumer state | Resource identity relevant here | Output-pair behavior | Reserved-pair role |
| :---- | :---- | :---- | :---- |
| Valid `entity_refs`; entity-aware mapping active; neither reserved key in any `id_keys` | The exact union referenced through all EntityRefs' `id_keys`; an attribute referenced by any entity remains identifying, while description-only and unreferenced attributes are non-identifying | Synthesize the Entity-derived pair, including UUIDv5 `instance`; do not consult legacy covered precedence or verbatim fallback | Descriptive scrape provenance, subject to the active-contributor proof |
| Valid `entity_refs`; entity-aware mapping active; either reserved key in any `id_keys` | The same exact union, including each referenced reserved key/value and any scrape-target domain context defined as identifying for that entity type | Synthesize the Entity-derived pair; `prometheus.scrape_target` references both reserved keys plus any identifying domain keys defined by its final semantic convention and therefore synthesizes from that complete set | Entity-identifying input, never descriptive contributor evidence; values remain queryable through the planned identifying-attribute or native-metadata path |
| Valid `entity_refs`; entity-unaware consumer | EntityRefs remain present on the Resource but do not affect that consumer's output | Use today's covered mapping and, when gated, whole-pair fallback | The payload role remains entity-identifying when a reserved key is referenced. An old consumer may treat it as ordinary metadata; an Option C-aware proof path records the identifying role even before synthesis is active. Upgrading synthesis can re-key output |
| Present malformed `entity_refs` | No Option C identity is synthesized from the malformed set or any subset | Follow the Entity and OTLP specifications; do not treat the set as absent and activate legacy or reserved fallback on its behalf | No new Option C role is inferred |
| No `entity_refs` | The present members of the legacy Prometheus identifying triplet: `service.namespace`, `service.name`, and `service.instance.id` | `job` from optional `service.namespace` plus `service.name`, `instance` from `service.instance.id`, then complete reserved-pair fallback if that mapping is incomplete | Descriptive outside the legacy triplet, or consumed verbatim as the fallback |

Option C's proposed EntityRef policy follows the producer rules above. A losslessly relayed declaration is authoritative. Only when no source declaration is present may the producer infer the complete application EntityRef set selected by its pinned policy and schema, and only from complete, reliable identifying values; flattened-name recovery is an explicit compatibility interpretation, not evidence that the application authored an entity. The document does not choose a combined or split service-entity decomposition. When entity-less resolution would consume the reserved pair because the legacy mapping is incomplete, the producer instead declares the sole working-name `prometheus.scrape_target` entity with the complete identifying set defined for that entity type. That entity represents the Prometheus metadata join identity in a label space, not the underlying application or the complete configured scrape-loop identity. The pair-only form `{type: prometheus.scrape_target, id_keys: [prometheus.job, prometheus.instance]}` is only a structurally encodable, pre-standardization experiment with its own pinned identity contract. It requires matching producer and consumer activation plus an explicit isolated-domain guarantee, must not escape that deployment, and is not a conforming instance of the final context-inclusive convention. The final semantic convention instead needs one fixed, minimally sufficient context-inclusive set whose stable, repeatable domain attributes are also referenced through `id_keys`. A producer that cannot reliably supply every identifying key remains entity-less. Partial covered attributes remain unreferenced, non-identifying Resource metadata; they are formal Entity descriptions only when named in `description_keys`. Covered attributes derived only from the scrape pair under today's defaulting create no entity, preserving the entity-less legacy path.

Do not infer the scrape-target entity alongside an inferred application EntityRef set under the recommended producer policy. Resource identity is the union across every EntityRef, not a choice of one preferred entity; carrying both would make the synthesized identity depend on application attributes and monitoring configuration together. A valid Resource received over OTLP may deliberately declare both identity domains; an entity-aware consumer preserves that decision and synthesizes from their combined union. A future producer relay likewise does not remove a valid source-authored combination, but it qualifies as exact only if the relay mechanism preserves every referenced attribute without collision or rebinding.

The planned mapping changes the guarantee. An entity-less fallback can restore the normalized pair byte-for-byte. An entity-bearing Resource instead gets the synthesized join pair: for `prometheus.scrape_target`, identity is stable for one Prometheus metadata join identity within its defined label-space domain, but `instance` is the UUIDv5 of the complete identifying union rather than the original scrape `instance` string. In the experimental isolated-domain pair-only profile that union is the reserved pair; under the interoperable context-inclusive definition, the referenced domain key/value pairs also enter the UUID input. The normalized pair alone carries no global-stability claim and does not identify a complete configured scrape loop. Different valid EntityRef declarations, including different types, decompositions, or schema versions, intentionally converge on the same synthesized `instance` when their exact referenced unions match, even though those declarations need not be merge- or relay-equivalent; convergence of the complete Prometheus pair additionally depends on the planned `job` rule. The original identifying values must remain queryable under that synthesized join key, with the exact native-metadata or `target_info` placement still open. For an application EntityRef set that does not reference the reserved keys, the reserved pair remains non-identifying scrape provenance and its exposure continues to require the contributor proof; that output role does not add it to `description_keys`.

Malformed EntityRefs remain governed by the Entity and OTLP specifications and do not create a new Option C fallback. A non-empty malformed set is never reclassified as no EntityRefs, and an implementation does not discard invalid members and synthesize from the remainder. Until entity-aware consumer support is active, valid entity-bearing payloads degrade to their flat entity-unaware behavior above. This mixed-version behavior is why consumer synthesis deploys before producer EntityRef emission.

### Round-Trip Use Cases

Concrete traces through the rules above, each naming its configuration. Cases assume underscores escaping unless noted; where stated, Option C's outcome is escaping-independent. Unless a case says otherwise, the consumer is a pull exporter whose complete active evidence contains only the shown Resource and whose loss-free interval is greater than its retention-covering proof horizon `R`, or whose continuity-qualified restore has completed with eligible untainted state, so it can prove the descriptive pair unique. A stateless push consumer omits that pair when the Resource-derived pair wins. Receiver-added enrichment (`server.address`, `server.port`, `url.scheme`) is omitted from the traces: it is unchanged by Option C and rides generated `target_info` as today.

#### R1 — Covered-present target: Prometheus → OTLP → Prometheus (both gates on)

An OTel SDK application behind the SDK's Prometheus exporter exposes `target_info{service_name="my_service", service_instance_id="my_instance_id"} 1`, scraped as `job="my_job"`, `instance="my_instance"`.

* Producer output: `Resource{prometheus.job="my_job", prometheus.instance="my_instance", service.name="my_service", service.instance.id="my_instance_id"}` — Option C interprets the `service_name` and `service_instance_id` forms on `target_info` as covered-mapping inputs (today they land as stray attributes while `service.name` holds the job). With no `entity_refs`, they enter the legacy Prometheus identifying subset. This is a lossy compatibility interpretation, not proof of application authorship or an entity declaration. The pair is descriptive. The Resource is the same whether the exposition negotiated `allow-utf-8` or `underscores`, and whether the flattening happened in the exposition or in the exporter beforehand — outcomes today diverge on both.
* Consumer output, `keep_identifying_resource_attributes=false`: `foo{job="my_service", instance="my_instance_id", A="B"}` and `target_info{job="my_service", instance="my_instance_id", prometheus_job="my_job", prometheus_instance="my_instance"} 1`.
* Consumer output, `keep_identifying_resource_attributes=true`: `foo{job="my_service", instance="my_instance_id", A="B"}` and `target_info{job="my_service", instance="my_instance_id", service_name="my_service", service_instance_id="my_instance_id", prometheus_job="my_job", prometheus_instance="my_instance"} 1`.
* Outcome: The complete covered mapping governs output end-to-end; `job`/`instance` differ from the original scrape labels — the deliberate Resource-pair-first shift (see Pros and Cons). The scrape coordinates are visible on `target_info` only because this consumer proved a single complete pair. With conflicting active contributors they are suppressed; with a stateless push consumer they are not emitted. Relative to today, the generated `target_info` identity labels shift, and today's stray `service_name`/`service_instance_id` labels are consumed into the covered attributes — present again only with `keep_identifying_resource_attributes`.

#### R2 — Covered-absent target, never-derive opted in: Prometheus → OTLP → Prometheus

node\_exporter scraped as `job="node"`, `instance="10.0.0.5:9100"`; no `target_info`.

* Producer output: `Resource{prometheus.job="node", prometheus.instance="10.0.0.5:9100"}` — no `service.*`.
* Consumer output (fallback): `node_cpu_seconds_total{job="node", instance="10.0.0.5:9100", cpu="0", mode="idle"}` and `target_info{job="node", instance="10.0.0.5:9100"} 1`. The generated info series uses the resolved fallback as its required identity, but does not additionally expose the consumed attributes as `prometheus_job` or `prometheus_instance`. In practice the omitted enrichment adds `server_address="10.0.0.5", server_port="9100"` to that `target_info`.
* Outcome: The ordinary series' `job` and `instance` round-trip byte-exactly through the gated fallback. Once the fallback supplies a complete output identity, the pull exporter's existing generation behavior additionally produces the identity-only `target_info`.

#### R3 — Covered-absent target, default derivation: Prometheus → OTLP → Prometheus

Same scrape as R2, never-derive not opted in.

* Producer output: `Resource{prometheus.job="node", prometheus.instance="10.0.0.5:9100", service.name="node", service.instance.id="10.0.0.5:9100"}` — derived as today; the covered mapping supplies a complete Resource-derived pair, so the fallback is dormant.
* Consumer output, `keep_identifying_resource_attributes=false`: `node_cpu_seconds_total{job="node", instance="10.0.0.5:9100", cpu="0", mode="idle"}` and `target_info{job="node", instance="10.0.0.5:9100", prometheus_job="node", prometheus_instance="10.0.0.5:9100"} 1` — legacy derivation from the derived `service.*`; the pair rides `target_info` descriptively. With `=true`, `service_name="node"` and `service_instance_id="10.0.0.5:9100"` additionally appear on `target_info`.
* Outcome: Ordinary-series labels are identical to today. With the consumer gate enabled and uniqueness proved, generated `target_info` gains the two pair labels; with the gate disabled they remain ordinary metadata under legacy behavior. With `=true`, the exposed `service_name`/`service_instance_id` labels make this target covered-present on a downstream scrape — derived values are indistinguishable from an application's own flat attributes and enter that entity-less scrape's legacy identifying subset.

#### R4 — OTLP-native origin: OTLP → Prometheus → OTLP (re-scrape with `honor_labels: true`, emission on)

Origin: `Resource{service.name="my_service", service.instance.id="my_instance_id", k8s.pod.name="p"}`, no pair.

* First consumer output, `keep_identifying_resource_attributes=false`: `foo{job="my_service", instance="my_instance_id"}` and `target_info{job="my_service", instance="my_instance_id", k8s_pod_name="p"} 1`.
* First consumer output, `keep_identifying_resource_attributes=true`: `foo{job="my_service", instance="my_instance_id"}` and `target_info{job="my_service", instance="my_instance_id", service_name="my_service", service_instance_id="my_instance_id", k8s_pod_name="p"} 1`.
* Re-scrape producer: the honored labels form the pair `("my_service", "my_instance_id")`. Three forks:
  * From the `keep_identifying=true` exposition: `Resource{prometheus.job="my_service", prometheus.instance="my_instance_id", service.name="my_service", service.instance.id="my_instance_id", k8s_pod_name="p"}` — the `target_info` labels restore the covered attributes with exact values. Note `k8s.pod.name` returns as `k8s_pod_name`: non-covered names are never un-escaped.
  * From the `keep_identifying=false` exposition, default derivation: `Resource{prometheus.job="my_service", prometheus.instance="my_instance_id", service.name="my_service", service.instance.id="my_instance_id", k8s_pod_name="p"}` — the same attribute set as the fork above, byte for byte: the target is covered-absent before derivation, so `service.*` are re-derived from the pair, enter the legacy identifying subset, and coincide with the originals. The flat Resource cannot prove whether an application or a translator authored those values.
  * From the `keep_identifying=false` exposition, never-derive: `Resource{prometheus.job="my_service", prometheus.instance="my_instance_id", k8s_pod_name="p"}` — `service.*` are absent; only scrape-provenance values matching the original covered values remain, not the original legacy identifying attributes (the fidelity gap Section 2's `keep_identifying` flip closes).
* Outcome: Value-lossless with `keep_identifying=true`; provenance-lossy or attribute-lossy without it.

#### R5 — Mixed versions: new producer, old consumer

* Covered-present target (R1's Resource) at an old or gate-disabled consumer (`keep_identifying_resource_attributes=false` shown): `foo{job="my_service", instance="my_instance_id", A="B"}` and `target_info{job="my_service", instance="my_instance_id", prometheus_job="my_job", prometheus_instance="my_instance"} 1`. The pair is ordinary metadata under existing rules; the consumer provides neither fallback nor collision-safe exposure guarantees.
* Covered-absent, never-derive Resource (R2's) at an old or gate-disabled consumer: `node_cpu_seconds_total{cpu="0", mode="idle"}` — no `job` or `instance` labels at all — and no `target_info` when no identity label is derivable. This is why consumer semantics must be enabled before never-derive (see Rollout).

#### R6 — Partial Resource mapping: OTLP → Prometheus

* `Resource{service.name="api", prometheus.job="scrape", prometheus.instance="10.0.0.8:8080"}` has one legacy Prometheus identifying attribute but no complete Resource-derived pair. The consumer uses the reserved pair whole: `foo{job="scrape", instance="10.0.0.8:8080"}`. It retains `service.name="api"` as Resource metadata and, where identifying-attribute exposure is enabled, as `service_name="api"` on `target_info`; it does not mix `job="api"` with the reserved instance. C.1 behaves identically, so enabling its consumer semantics also changes this Resource from today's partial `foo{job="api"}` output.
* The same Resource without a reserved pair keeps legacy output, `foo{job="api"}` with no `instance`, and emits no new diagnostic. `service.instance.id` alone analogously produces only `instance`; `service.namespace` alone produces neither.
* A valid entity-bearing version does not use this fallback at an entity-aware consumer; it follows R8. An entity-unaware consumer still sees the flat attributes and behaves as above.

#### R7 — Encoded provenance-name collision

Under underscore output, `prometheus.job` and an ordinary Resource attribute named `prometheus_job` both map to `prometheus_job`. With the gate enabled, the pair handler owns that output name before generic projection. If a complete Resource-derived pair wins and provenance is proved, the exact reserved pair is emitted and the ordinary colliding attribute is omitted with one bounded diagnostic. If the pair is consumed as fallback or is invalid, conflicting, missing, or unprovable, neither reserved output name is emitted and the ordinary colliding attribute is still omitted, so it cannot masquerade as provenance. Where no complete output pair exists, the diagnostic is bounded by Resource rather than pair. Gate-disabled output retains today's ordinary collision behavior.

#### R8 — Planned entity-aware mapping

These cases assume entity-aware producer emission and consumer synthesis are active. The symbolic `job` values and identifying-attribute placement remain owned by the planned Prometheus mapping; `instance` follows its UUIDv5 synthesis over the shown identifying union. The scrape-target examples use the pre-standardization pair-only experiment under matching pinned producer and consumer profiles plus an explicit single-label-space isolation guarantee; they illustrate the join-identity mapping but are neither a generic interoperable wire form nor conforming examples of the final convention. Under the final context-inclusive semantic convention, the examples add every minimally sufficient, stable, repeatable domain attribute to the Resource, `id_keys`, and the shown UUID input; a producer missing them remains entity-less and uses the verbatim fallback.

* **Reliable complete application identity** — R1's Resource additionally carries the complete application EntityRef set selected by the producer's pinned policy and schema, whose combined identifying union is `{service.name="my_service", service.instance.id="my_instance_id"}`. The consumer emits `foo{job="<planned entity job>", instance="<UUIDv5 of {service.name=\"my_service\", service.instance.id=\"my_instance_id\"}>", A="B"}`. The reserved scrape pair is not in `id_keys`, so it remains non-identifying scrape provenance and appears on generated `target_info` only under the complete-contributor proof; it is a formal Entity description only if a source declaration includes it in `description_keys`. Directly pushed telemetry with the same exact referenced union under a compatible resolver synthesizes the same `instance`; EntityRef and `id_keys` order and an equivalent decomposition do not change the UUID input, while complete-pair equality also requires the planned `job` rule to produce the same value.
* **Partial service mapping** — R6's Resource additionally carries only the experimental pair-only `{type: prometheus.scrape_target, id_keys: [prometheus.job, prometheus.instance]}` under the matching pinned profiles and explicit isolated-domain guarantee assumed here. `service.name="api"` remains unreferenced, non-identifying Resource metadata rather than a formal description of the scrape-target entity. The consumer emits `foo{job="<planned entity job>", instance="<UUIDv5 of {prometheus.job=\"scrape\", prometheus.instance=\"10.0.0.8:8080\"}>"}`. The original pair is entity-identifying for the Prometheus join identity, not descriptive provenance, and remains queryable through the planned identifying-attribute or native-metadata representation.
* **Covered-absent, never-derive** — R2 carries the same sole experimental scrape-target join entity over `("node", "10.0.0.5:9100")` under matching pinned profiles and the same isolation guarantee; its output `instance` is the UUIDv5 of those identifying values rather than the byte-exact source string. This is the pre-standardization entity counterpart of the verbatim fallback, not a conforming instance of the final context-inclusive convention.
* **Covered-absent, default derivation** — R3 carries no EntityRefs. Its `service.*` values were derived from the scrape pair rather than reliably asserted as an application entity, so legacy label derivation and byte-exact output remain unchanged until never-derive or another explicit entity policy is activated.

At an entity-unaware consumer, the application-entity case degrades to R1's covered mapping and the scrape-target cases degrade to R6 or R2's gated verbatim fallback. Enabling entity synthesis later re-keys those series to the planned pair. An intermediary that drops EntityRefs causes the same semantic downgrade and is not transparent.

### Non-goals

- Identity-precedence configuration: No option exists to make the reserved pair outrank a complete Resource-derived pair.
- Byte-exact `job`/`instance` label round-trips where a complete Resource-derived pair exists, or for entity-bearing payloads: Resource-pair-first or entity synthesis deliberately re-keys those series.
- Partitioning Resources that map to the same output identity: the pair does not split them, and conflicting provenance is suppressed rather than selected.
- Redesigning consumer-side reduction of non-pair Resource metadata into generated `target_info`, or its grouping, scheduling, or lifecycle. Producer-side source-`target_info` association remains in scope and follows the active-contributor agreement and `H` rules above.
- Cross-request or cross-output-unit delivery atomicity, batch envelopes, deduplication, exactly-once semantics, and protocol response or accounting changes.
- Preservation of source `target_info` sample timing beyond observation ordering and association: protocol staleness remains authoritative, while a stateful push producer additionally applies `H` only to its retained association state.

### Requirements Mapping

- **Separate Storage**: Satisfied for accepted, unambiguous metadata while association state is usable — the reserved pair and covered attributes are distinct Resource attributes and never overwrite each other. During startup or state loss, cross-request producers deliberately suppress association-derived covered metadata rather than emit an unproved value. With a valid EntityRef set, only Resource key/value pairs referenced through `id_keys` enter the entity-declared identity; the reserved pair remains non-identifying scrape provenance unless referenced, and that output role does not make it a formal Entity description. Without EntityRefs, flat covered attributes and recovered aliases enter the legacy Prometheus identifying subset by policy. Neither case establishes who authored a recovered value.
- **Complete Join Key When Available**: Entity-aware translation synthesizes one complete pair from the entity-declared identifying union. Otherwise, a complete Legacy Resource-derived pair wins, then a valid reserved pair supplies both values. No path combines partial sources. When no applicable source is complete, legacy partial or absent output remains, so Option C does not claim an unconditional pair for arbitrary incomplete native OTLP input. Conflicting provenance never changes the resolved join key.
- **Queryable Resource Attributes**: With never-derive in effect, Option C does not write scrape-configuration strings into covered attributes. When the entity-less fallback supplies output identity, partial covered attributes remain inputs to the legacy identifying subset even though they do not contribute to the resolved output pair. When a scrape-target entity supplies output identity, covered attributes that no EntityRef references remain non-identifying Resource metadata and become formal Entity descriptions only through `description_keys`. Under entity-aware synthesis, every referenced identifying value must remain queryable under the synthesized join key; its exact native-metadata or `target_info` placement remains open. Descriptive provenance visibility is conditional on the active-contributor proof and is not guaranteed when a Resource-derived pair wins.
- **Non-Breaking Server Compatibility**: Defaults are unchanged while producer reserved-pair emission, consumer reserved-pair semantics, entity-aware synthesis, and producer EntityRef emission are disabled. Enabling any control changes the corresponding translation surface and requires an explicit rollout. Any future default flip is a separate compatibility decision; Option C does not pre-classify it as non-breaking.

One consequence is deliberate: With never-derive in effect, a covered-absent target yields a Resource with **no `service.*` at all**. The fallback supplies its output `job`/`instance`, but generic OTel consumers group such Resources as service-less rather than under a scrape-configuration-derived name — per Practical Issue 3, an absent service identity is preferable to a polluted one. This requires the compatibility specification to permit non-derivation on Option C producer paths. Section 1's opt-out already lets other options switch defaulting off; Option C adds a defined fallback and rollout order.

Operators who prefer job-derived service names can still create them deliberately — e.g. an OTTL statement such as `set(resource.attributes["service.name"], resource.attributes["prometheus.job"])` — turning the derivation into an explicit per-pipeline choice rather than a default; such a processor is semantics-changing and intentionally outside the contract.

### Pros and Cons

Pros:

* **Default compatibility is explicit**: With all new controls disabled, producer and consumer behavior remains legacy behavior. Adoption is deliberate and independently staged.
* **The complete Resource-derived pair has precedence**: Where existing Resource translation supplies both labels, series use the same source as native OTLP translation rather than being re-keyed by where Prometheus scraped them.
* **The stated pollution and jobless-output pains are addressed for eligible Prometheus-origin payloads**: With never-derive in effect, scrape producers and complete-pair Remote Write series do not write scrape-configuration strings into `service.name`, while their complete reserved pair supplies the legacy fallback or the reserved-key portion of the scrape-target entity's identifying input whenever matching pinned pre-standardization profiles plus an explicit isolation guarantee or the complete final context-inclusive definition is satisfied and application Resource mapping cannot supply a complete pair. Incomplete Remote Write series retain legacy behavior by design.
* **Provenance-safe names**: `prometheus.job`/`prometheus.instance` state their origin, so a consumer does not have to guess whether an attribute named `job` means scrape identity.
* **Collision-safe metadata**: Generated `target_info` never advertises one arbitrary contributor's scrape coordinates or re-labels a consumed fallback as description. Conflicting, role-mixed, or unprovable provenance is omitted atomically.
* **Bounded inference**: Underscore recovery is limited to three covered names and is explicitly opt-in; Variant C.1 removes even that interpretation.
* **Entity-era roles remain separate**: A reliably declared application EntityRef set drives synthesized identity, while an entity-less fallback can become a sole scrape-target join entity when its complete convention-defined identity is reliable. Before standardization, the pair-only experiment requires matching pinned producer and consumer profiles plus an explicit isolation guarantee; otherwise the Resource stays entity-less. The producer does not mask application identity with scrape coordinates or infer both roles by default.

Cons:

* **Resource-pair-first re-keys Prometheus series**: A series with a complete Resource-derived pair re-enters Prometheus under that pair rather than the original scrape labels. Dashboards, rules, and alerts keyed on the source pair must migrate. Without active entity synthesis, an incomplete covered mapping instead uses a complete reserved fallback when present, so monitoring configuration still supplies the operational join for that class.
* **Covered-absent targets are service-less on OTel-native backends**: An absent service identity is preferable to a polluted one, but with never-derive in effect their grouping regresses relative to defaulting; explicit derivation is the mitigation.
* **Convergent identities hide multiple origins and can collide as writers**: Resources mapping to the same output identity merge under existing behavior. Option C preserves that join but suppresses conflicting scrape provenance, so one `target_info` cannot represent every origin. Identical metric series from those origins may also become duplicate writers or collide in an existing last-value accumulator; contributor proof prevents false metadata attribution but performs no sample deduplication and adds no exactly-once delivery guarantee.
* **Stateless push cannot expose descriptive provenance safely**: It must omit the pair whenever the Resource-derived pair wins because it cannot prove the active contributor set across requests.
* **Producer-side machinery**: Profile selection, covered-name recovery with collapse and conflict rules, target-metadata association, and pair-keyed grouping with cross-request state on push paths are new producer work. Variant C.1 removes lossy covered-name recognition, but not the association lifecycle needed for other metadata.
* **Cross-request producer recovery is conservative**: Stateful push producers require an explicit refresh contract. Startup without continuity-qualified state, failed restore, and capacity loss suppress all `target_info`-derived Resource metadata across the association-state scope through exactly `H`; recovery can then re-key Resource grouping and series when the covered mapping returns and, without `entity_refs`, changes the legacy Prometheus identifying subset. Avoiding that interval requires cursor-coupled durable replay or a fenced no-gap handoff, which current Collector receivers do not provide.
* **Consumer-side machinery**: Consumers need one pair resolver used by labeling and grouping, atomic pair validation, encoded-name reservation, an exact Consumer series key, role-aware contributor agreement, a positive finite `R` covering every accumulated value's inactivity-retention interval, bounded state, a scope-wide fail-closed overflow epoch, consistent exposition snapshots, and transition-bounded proof diagnostics. Stateful implementations must connect the proof to their existing retirement lifecycle; restart continuity additionally requires cursor-coupled durable replay or a fenced no-gap handoff.
* **Generated `target_info` may reshape at adoption**: Where uniqueness is proved, the pair adds two labels and changes the info series. Where uniqueness is not proved, provenance is absent.
* **Underscore recovery is lossy**: A label named `service_name` cannot be distinguished from an attribute literally named `service_name`. Treating it as `service.name` is an opt-in compatibility interpretation, not a reversible mapping or authorship signal.
* **Output identity changes when the legacy Resource mapping becomes complete or incomplete**: When entity-aware synthesis is not active, the target flips between fallback and the Legacy Resource-derived pair, breaking its series once.
* **Proof recovery is conservative**: Without stable contributor identity, changed, missing, or stale provenance evidence suppresses descriptive labels through exactly `R` and until the first consistent snapshot after that boundary. Cold start without continuity-qualified state and high-churn overflow suppress provenance throughout the bounded proof-state scope rather than risk false provenance or retain unbounded per-pair taints. A consumer without a positive finite `R` covering every accumulated value's inactivity-retention interval cannot expose descriptive provenance statefully.
* **Gate activation reserves output names**: Existing Resource attributes that encode to the pair's `target_info` label names are omitted from generated metadata while the gate is enabled, even when no descriptive pair is emitted.
* **Standardization is a prerequisite**: Reserved-name registration, fallback semantics, collision-safe exposure, and permission for never-derive must land before conforming implementations can ship.
* **The namespaced prefix must be learned**: OTTL and processor work targets `prometheus.job`, not `job`.
* **Entity-bearing output is not byte-exact**: Planned entity-aware ingestion synthesizes `instance` as UUIDv5 over the complete identifying union, including for a scrape-target entity. The original identifying values therefore need a queryable metadata representation.
* **Entity inference is schema-sensitive**: A producer may declare an application EntityRef set only when it can reliably supply the complete identifying set required for every emitted entity by its pinned semantic-convention schema. Producer and consumer policy/schema versions become compatibility state. Synthesized-`instance` convergence depends on a compatible resolver and the same exact referenced key/value union, while complete-pair convergence additionally depends on the planned `job` rule; neither follows from one hard-coded combined or split service-entity decomposition.
* **The scrape-target entity is a standardization dependency**: Its final type name, join-identity semantics, identity domain, fixed complete identifying set, `job` synthesis, UUID canonicalization, and identifying-value placement must be specified before entity-era emission is interoperable. The pair-only form is a pre-standardization experiment, not a conforming instance of that final entity: it is safe only with matching pinned producer and consumer profiles behind an explicit isolated-domain guarantee and is not self-describing on the wire. The interoperable semantic convention therefore needs a minimally sufficient context-inclusive set that always references its required stable, repeatable domain attributes through `id_keys`. The separately versioned Prometheus mapping consumes that convention-defined union but does not supply an identity domain.

### Comparison with Options A and B

| Aspect | Option A (bare) | Option B (namespaced) | Option C |
| :---- | :---- | :---- | :---- |
| Resource attributes | `job`, `instance` | `prometheus.job`, `prometheus.instance` | Same as B |
| Role of the stored pair | Authoritative output identity, looked up first; server-side once `honor_labels` is enabled | Authoritative output identity at aggregated exporters (Section 1); at the Prometheus server, gated by Section 2's `honor_labels`, off by default today | Entity-identifying when referenced through `id_keys`; otherwise descriptive provenance when the applicable Resource mapping supplies a complete pair, or a whole-pair legacy fallback when it does not |
| Consumer activation | Requires the `honor_labels` server flag: Bare names are generic, unreservable attribute keys a consumer cannot distinguish from scrape identity — whether they already occur in OTLP traffic is unmeasured, but they remain open to collision permanently | No disambiguation flag needed, the name being self-describing, but Section 2's `honor_labels` still gates the server until its major-version flip | One implementation-specific, default-disabled gate for pair recognition, fallback, and collision-safe exposure |
| `service.*` defaulting from job/instance | Core Rules MAY-default plus toggle | Core Rules MAY-default plus toggle | MAY-default; never-derive separately opt-in, with any future default flip treated as a compatibility decision |
| Breaking risk | Several flows marked BREAKING in the tables above | Low today; the `honor_labels` flip shifts output identity for pair-bearing payloads at a major version | Defaults unchanged while producer emission and consumer semantics are disabled; each enablement and any default flip is a compatibility decision |
| Collector / OTTL UX | Natural label names | Prefix must be learned | Prefix must be learned |
| Semantic-convention registration | Arguably none needed | Needed | Needed, as reserved descriptive names plus fallback semantics |
| Entity data model compatibility | Pair-first can remain byte-exact only on entity-unaware or entity-less paths; declaring either pair as identifying subjects it to entity synthesis | Same: B's byte-exact promise is conditional on the pair remaining outside entity-declared identity | A valid EntityRef set takes precedence and synthesizes from its exact identifying union; without one, use the legacy covered mapping and whole-pair fallback |

On the central entity-less difference — precedence — the options choose which output continuity to preserve. Pair-first preserves source Prometheus series identity and lets scrape coordinates displace the complete pair produced by the covered Resource mapping. Option C preserves that mapping's output continuity when it supplies a complete pair, and uses scrape coordinates whole when it does not. Entity-aware input adds a separate constraint: the planned mapping synthesizes from the EntityRef-declared identifying union, so a pair-first design must either remain entity-less, accept synthesis, or define a carve-out. Current PromQL `info()` behavior is evidence for the practical importance of `job` and `instance` today: it treats them as identifying labels for info metrics, and classic joins commonly rely on them. That implementation is not assumed to be a permanent invariant. Option C therefore specifies join behavior for today's model while keeping descriptive provenance exact and collision-safe, then composes that behavior with planned entity synthesis.

Variant C.1 below shares Option C's column above, save for the Breaking risk row: For entity-less targets whose covered names reach the producer flattened, it declines the lossy interpretation, which keeps their `job` and `instance` labels byte-exact but forfeits continuity with the same covered values pushed over OTLP, and makes its own producers emit the colliding Resource that Option C avoids. Once C.1 emits an EntityRef, the planned synthesis rules apply and that byte-exact property ends.

#### Who changes, by input path

The main entity-less compatibility classes are determined by how an application's exposition names things and by whether Resource translation supplies a complete pair. Each cell is the resulting `job` label; entity-bearing outcomes are covered by R8 and V4.

| Input path | Today | Option B | Option C | Variant C.1 |
| :---- | :---- | :---- | :---- | :---- |
| OTLP pushed directly, no reserved pair | `service.namespace/service.name` | Unchanged | Unchanged | Unchanged |
| Prometheus SDK exporter, default settings — `target_info` carries `service_name` | The scrape `job` | The scrape `job` | **`service.name`** — policy interprets the flattened form | The scrape `job` |
| Prometheus SDK exporter with `NoTranslation` — `target_info` carries `service.name` | `service.name`, by key coincidence at the receiver | **The scrape `job`** | `service.name` | `service.name` |
| Partial Resource mapping plus a valid reserved pair — for example, only `service.name="api"` | `api` (with no `instance`) | The scrape `job` — pair-first | The scrape `job` — whole-pair fallback | Same as C |

The default-settings row is the populous one, since the Go SDK exporter has defaulted unconditionally to underscore escaping since v0.62.0 (`newConfig` in `exporters/prometheus/config.go`), and `NoTranslation` is both newer and, by the exporter maintainers' account, unevenly implemented across languages. So Option C changes the `job` label for more deployments than Option B does. Variant C.1 avoids that change for the complete flattened case, at the price of leaving Practical Issue 3 unfixed there, but it shares C's whole-pair fallback and therefore still changes partial pair-bearing Resources.

Changing a label is not the same as breaking a consumer, and the two diverge here. A Grafana application team reports deriving service name and namespace from `job`, with a service-overview dashboard keyed on it for RED metrics. On the flattened row that assumption holds only where the scrape job happens to be named for the service, `job` otherwise carrying an unrelated scrape-configuration string: Option C makes `job` carry the Resource-side service name and namespace, as on the push path, while B leaves the scrape string in place. On the dotted row the assumption holds today: C preserves it, B replaces `job` with the scrape job. The populous row's change under C therefore cuts both ways — it breaks dashboards and rules keyed on the old value, and it repairs consumers that read `job` as a service name. Preserving that row's `job` label and fixing its `service.name` pollution are the same decision seen from two sides. Option B's column assumes its pair-first lookup is active. Option C and C.1 require their own reserved-pair semantics gate for fallback and descriptive exposure; Resource-pair-first derivation itself matches the endpoint's legacy precedence.

Covered-attribute retention is a separate axis from precedence, and the options do not differ on it. Whether those attributes survive the hop as `target_info` labels is what `keep_identifying_resource_attributes` governs, and Section 2 already plans its default flip; B, C, and C.1 can each retain or drop them. Option C's retention-covering consumer proof state is separate machinery for descriptive provenance, not a covered-attribute retention control. Producer cross-request association retention is likewise implementation machinery rather than a precedence choice, but any implementation that uses it needs the fail-closed `H` contract above. Collector deployments have no `keep_identifying` control today — contrib's Remote Write translator removes all three covered attributes unconditionally — so a complaint about `service.*` being stripped is an argument for that flip and for contrib parity, not for any option in this document.

#### Option B stated as pros and cons

Option B, as this document specifies it, is the reserved pair under namespaced names with Section 1's pair-first lookup: `prometheus.job` and `prometheus.instance` are stored on the Resource and consulted before the covered `service.*` subset. It is therefore Option C's storage decision with the opposite precedence, and the pros and cons below are meant to state it at full strength rather than as a foil.

Pros:

* **Byte-exact `job`/`instance` round-trips without active entity synthesis**: Scrape coordinates come back verbatim whatever flat Resource-side attributes are present — at aggregated exporters today, and at the Prometheus server once Section 2's `honor_labels` default flips — so dashboards, rules, and alerts keyed on them survive the OTLP hop. Relative to today's output, B changes dotted exposition by displacing its Resource-derived pair and changes partial pair-bearing Resources by replacing their legacy partial output. A valid EntityRef set makes this benefit conditional as described below.
* **Its precedence changes are gateable**: B changes dotted exposition and any currently partial Resource mapping that carries a valid reserved pair. A per-scrape or consumer opt-out or opt-in covers those migrations; the complete flattened default has nothing to migrate because its `job` never carried the Resource-side value.
* **Provenance-safe names**: Shared with C — a consumer never has to guess whether an attribute means scrape identity, and no flag is needed to disambiguate what the attribute means, though Section 2's `honor_labels` still gates when the server honors it.
* **No accidental collision with existing OTLP attributes**: `prometheus.job` is a new reserved name, so activation changes output identity only through the specified pair precedence, not by reinterpreting an existing bare `job` attribute — the axis on which Option A breaks.
* **Least producer machinery**: Storage plus the existing derivation, with no covered-name recovery and no fallback semantics. The target-metadata association questions Option C specifies arise for B too, on push paths especially; B leaves them to existing implementation behavior rather than answering them.
* **It pushes the ecosystem toward native metadata**: Keeping `job` and `instance` as scrape coordinates strengthens the case for entity handling and for consuming resource attributes from `target_info` rather than from identity labels — the reason its proponents favour it, who hold that this migration is wanted anyway.

Cons:

* **It makes the scrape target's coordinates authoritative for Prometheus output**: An application with a complete `service.*` mapping has those attributes stored and then ignored for output identity, so scrape identity displaces the complete covered-derived pair — the mirror image of Practical Issue 1, and the objection Option C's complete-Resource-pair-first order exists to answer. Because the output pair is also the `target_info` join key, application metadata is re-keyed when its scrape job is renamed, and the same application scraped and pushed does not share an output identity. That Resources sharing one target are indistinguishable is not a difference between the options: Every option groups a scrape by the normalized pair, so one target yields one Resource.
* **It falsifies a common consumer assumption**: Consumers that read service name and namespace out of `job` — a practice reported in at least one production dashboard suite — keep working on the pushed path, lose the assumption on the dotted path, and stay wrong on the flattened path, where `job` remains a scrape-configuration string they misread as a service name. Resource-pair-first repairs the last case rather than preserving it.
* **Output identity is path-dependent**: The same application scraped and pushing OTLP directly can land under two output pairs, so its series do not merge; Option C instead preserves the complete Resource-derived pair where the same values survive both paths.
* **`service.name` pollution is left to each deployment**: Section 1's mandatory opt-out lets a B deployment switch the defaulting off, but B neither names the setting nor plans a default flip, so scrape-config strings occupy the semantic slot unless an operator intervenes — Practical Issue 3 persists by default.
* **Its entity story requires a policy exception or loses byte-exactness**: If B remains entity-less, its pair-first output can stay verbatim but does not participate in entity-declared identity. If it declares `prometheus.job` and `prometheus.instance` as a scrape-target entity, planned UUIDv5 synthesis replaces the original `instance`. If it instead carries an application EntityRef set and still lets the scrape pair win, the consumer needs a carve-out that overrides entity identity. Declaring both roles does not create a choice between them: the identifying union contains both application and scrape attributes.
* **Its central promise waits on a flag flip**: Byte-exact round-tripping through Prometheus's own OTLP endpoint requires `honor_labels=true`, which Section 2 defers to a future major version. Option C's complete-Resource-pair-first precedence matches the endpoint's present derivation order where that mapping is complete, although Option C's fallback and descriptive exposure still require its separate consumer gate.

The options therefore separate three decisions. Naming — bare or namespaced — is settled jointly by B, C, and C.1 against A. On entity-less paths, namespaced storage still leaves precedence when the legacy Resource mapping supplies a complete pair: pair-first (B) or Resource-pair-first (C, C.1), followed by whether the producer recovers flattened covered names (C) or leaves them as metadata (C.1). On entity-bearing paths, each option must additionally either honor synthesis from the complete EntityRef-declared union or specify an explicit incompatibility; C and C.1 choose synthesis.

### Variant C.1: Without Covered-Name Recognition

Option C.1 is Option C with one rule removed: The producer does not recover the covered names from their underscore forms on `target_info`. Decoding stays — `dots` and `values` encodings are reversed as before, recoverably for the three covered names — so only the lossy interpretation is dropped, and a decoded label named `service_name` remains an ordinary Resource attribute of that name. Everything else is identical: the reserved pair, never-derive, the whole-pair fallback when Resource translation is incomplete, the consumer gate, the contributor-proof rule, and the entity-era precedence and emission policy. Two things follow. C.1 confines to recoverable encodings its departure from the specification's default that label keys are not altered, inferring no covered name from a lossy form — though it still asks for reserved-name registration, fallback and never-derive semantics, and permission for non-derivation. Its normative delta exceeds a deleted recognition step: the rule that covered attributes from `target_info` are preserved under their dotted names must be relaxed when an exporter has already flattened them. In the entity era, that missing recovery can also change which entity can be declared.

The difference appears wherever a covered name is in a bare underscore form once the wire encoding is decoded. An exporter that sanitizes attribute names at record time produces one, as does exposition negotiated at `underscores`; so does an attribute literally named `service_name`, which reaches that form under every profile — escaped and decoded again under `dots`, never escaped at all under `values`. Such a target has no covered attributes under C.1, so it is covered-absent before any legacy derivation, and an attribute genuinely named `service_name` keeps its name instead of being reinterpreted. Where exposition carries the dotted names the two designs coincide, and targets that expose no `target_info` at all (R2, R3) are unaffected.

#### Round-Trip Use Cases for C.1

R1's scrape throughout, with producer emission and consumer semantics enabled: an OTel SDK application behind the SDK's Prometheus exporter exposes `foo{A="B"}` and `target_info{service_name="my_service", service_instance_id="my_instance_id"} 1`, scraped as `job="my_job"`, `instance="my_instance"`. As in R1, the shown consumer is a pull exporter whose loss-free interval is greater than its retention-covering proof horizon `R`, or whose continuity-qualified restore has completed with eligible untainted state, so it can prove a singleton active contributor set.

**V1 — Flattened exposition, default derivation**

* Producer output: `Resource{prometheus.job="my_job", prometheus.instance="my_instance", service.name="my_job", service.instance.id="my_instance", service_name="my_service", service_instance_id="my_instance_id"}` — the exposed labels are kept verbatim and are not covered attributes, so the target is covered-absent before `service.*` are derived from the pair as today and enter the entity-less legacy identifying subset. Both spellings sit on one Resource with different values: `service.name` holds the scrape config, `service_name` holds the application.
* Consumer output, `keep_identifying_resource_attributes=false`: `foo{job="my_job", instance="my_instance", A="B"}` and `target_info{job="my_job", instance="my_instance", prometheus_job="my_job", prometheus_instance="my_instance", service_name="my_service", service_instance_id="my_instance_id"} 1`.
* Consumer output, `keep_identifying_resource_attributes=true`: `foo{job="my_job", instance="my_instance", A="B"}` and `target_info{job="my_job", instance="my_instance", service_name="my_job", service_instance_id="my_instance", prometheus_job="my_job", prometheus_instance="my_instance"} 1` — the derived covered attributes translate to `service_name` and `service_instance_id`, the same label names the verbatim attributes already carry, so covered output names take precedence and the application's values are omitted with a bounded diagnostic. This is a regression against today rather than only against Option C: today's consumer joins colliding values, emitting `service_name="my_job;my_service"`, so `my_service` survives. It is also confined to escaped output — under a UTF-8-preserving output translation the two names never collide and both survive.
* Outcome: Ordinary-series labels are byte-identical to today's scrape, which is the compatibility gain. With uniqueness proved, the two pair labels are added to generated `target_info`; a stateless push consumer omits them. The application's own identifiers ride along on the Resource but are never read as covered-mapping inputs, and under Section 2's planned `keep_identifying` default flip they are dropped from the output entirely.

**V2 — Flattened exposition, never-derive opted in**

* Producer output: `Resource{prometheus.job="my_job", prometheus.instance="my_instance", service_name="my_service", service_instance_id="my_instance_id"}` — no `service.*` at all; the exposed labels remain ordinary attributes.
* Consumer output (fallback): `foo{job="my_job", instance="my_instance", A="B"}` and `target_info{job="my_job", instance="my_instance", service_name="my_service", service_instance_id="my_instance_id"} 1` — the resolved pair supplies the generated info series' identity labels, but the consumed Resource attributes are not additionally exposed under their reserved descriptive names. With no covered attributes present no output name collides, so the application's values survive.
* Outcome: The variant's best case — byte-exact `job`/`instance` and the application's own values preserved, but only as flattened metadata: A generic OTel consumer sees a service-less Resource and cannot group these series with the same application's traces.

**V3 — Dotted exposition (`allow-utf-8`)**
The same application, exposing \`target\_info{"service.name"="my\_service", "service.instance.id"="my\_instance\_id"} 1\`.

* Producer output: `Resource{prometheus.job="my_job", prometheus.instance="my_instance", service.name="my_service", service.instance.id="my_instance_id"}` — identical to R1 under Option C: the dotted names need no recovery.
* Consumer output, `keep_identifying_resource_attributes=false`: `foo{job="my_service", instance="my_instance_id", A="B"}` and `target_info{job="my_service", instance="my_instance_id", prometheus_job="my_job", prometheus_instance="my_instance"} 1` — identical to R1.
* Outcome: C.1 and C coincide here, costs included: this target takes the Resource-pair-first shift and its output labels stop matching the scrape. Which case a deployment lands in is therefore decided by its exporter's naming rather than by its configuration.

**V4 — Planned entity-aware mapping**

* Flattened exposition with never-derive follows V2's entity-less fallback decision. Under matching pinned experimental producer and consumer profiles plus an explicit single-label-space isolation guarantee, the producer may emit the sole pair-only `{type: prometheus.scrape_target, id_keys: [prometheus.job, prometheus.instance]}` join-identity EntityRef and the consumer synthesizes `instance` as UUIDv5 over those identifying values. This is a structurally encodable pre-standardization experiment, not a generally interoperable wire form or a conforming instance of the final convention. Under the final context-inclusive semantic convention, the producer adds every required minimally sufficient, stable, repeatable domain key to the Resource, `id_keys`, and UUID input; without the complete set, it remains entity-less and uses the verbatim fallback. The flattened application values remain unreferenced, non-identifying Resource metadata rather than formal scrape-target Entity descriptions, and an emitted entity makes the result no longer a byte-exact round-trip.
* Flattened exposition with default derivation follows V1 and emits no EntityRef: the covered values were derived solely from the scrape pair and the application-looking underscore attributes were not accepted as covered identity. It therefore remains on the legacy entity-less path.
* Dotted exposition can declare the application EntityRef set selected by the pinned policy and schema only when every identifying value for every emitted entity is accepted and reliable. Its synthesized `instance` can then converge with directly pushed telemetry when the consumer uses a compatible resolver and the exact referenced key/value union matches; complete-pair convergence additionally depends on the planned `job` rule. Thus C.1 and C do not have one universal entity-era outcome: their covered-name policy can select scrape-target, application-entity, or entity-less behavior.

#### C.1 Pros and Cons

The lists below are the delta against Option C. Resource-pair-first treatment of covered attributes and the pollution fix apply to dotted exposition only under C.1. The rest carries over unchanged: the Resource-pair-first shift for dotted exposition, handling of convergent output identities, the consumer proof rule, the standardization prerequisites, the namespaced prefix, and the producer-side machinery minus covered-name recovery.

Where C.1 beats C:

* **No covered name is inferred from a lossy form**: Option C's objection to inferring meaning from a bare attribute name applies to no part of C.1, and the recognition cost disappears — an attribute named \`service\_name\` is neither consumed nor reinterpreted.
* **Compatibility for the flattened class**: The Resource-pair-first shift narrows to dotted exposition, so targets behind flattening exporters keep their scrape labels end to end and the objection that Option C changes today's output stops applying to them.
* **No additional precedence-driven change for complete flattened or dotted mappings**: C.1 keeps the scrape `job` for the complete flattened case and today's Resource-derived `job` for the complete dotted case. It still shares Option C's whole-pair fallback, so a partial Resource mapping with a valid reserved pair changes to the complete scrape pair (see Who changes, by input path and R6).
* **Smaller surface**: No underscore recovery and a narrower specification ask — permission to reverse recoverable encodings rather than to reinterpret a lossy one. Collapse and conflict handling still applies, since two wire labels can decode to one name.
* **The guess stays available**: An operator who wants it renames `service_name` to `service.name` in the pipeline, making it an explicit per-pipeline choice. The mitigation sits downstream of the producer, since covered-attribute assignment happens inside the receiver and nothing can precede it. It must overwrite V1's already-derived value. Like the derivation OTTL above, it is semantics-changing and intentionally outside the contract.

Where C beats C.1:

* **Visible Resource metadata is deliberately not interpreted as a covered mapping input**: The application's likely covered values are present in the payload but ambiguous, so Practical Issues 1 and 3 persist for flattened exposition — under default derivation `service.name` carries the scrape-configuration string while the other value sits under a key no generic OTel consumer interprets.
* **It leaves a consumer reading dependent on convention**: Because the populous path keeps its scrape `job`, consumers that read service name and namespace from `job` remain dependent on operator naming convention there, correct only where a job is named for its service. C.1 buys label stability at the cost of leaving that reading unreliable, where a complete Resource-derived pair makes it correct for the covered values by policy.
* **The likely application values can be destroyed on output**: In V1 with `keep_identifying_resource_attributes=true` — Section 2's planned default — the derived covered attributes claim the `service_name` output labels and the flattened values are dropped with a diagnostic, where today's consumer joins them and keeps both; UTF-8-preserving output avoids the collision entirely.
* **No covered-attribute or output continuity for the flattened class**: Such a scraped application uses scrape-derived covered attributes while the same application pushing OTLP uses its native Resource attributes; dotted exposition avoids that divergence, per V3.
* **The outcome follows exporter naming**: Two deployments of one application land in different covered-mapping classes depending on whether its exporter flattens, which no scrape-side setting corrects; only a pipeline rewrite does, with the caveats above.
* **Entity paths diverge for flattened exposition**: With never-derive, C.1 can declare the scrape-target entity rather than an application EntityRef set only under matching pinned pre-standardization pair-only profiles with an explicit isolation guarantee or when the complete final context-inclusive identifying set is reliable; otherwise it remains entity-less and uses the fallback. With default derivation it declares no entity. Dotted or directly pushed telemetry can instead carry application EntityRefs, so synthesized-`instance` convergence requires the same exact referenced union under a compatible resolver, complete-pair convergence additionally depends on the planned `job` rule, and neither can be inferred from similar flat values.

Against the document's requirements, C.1 answers differently in two places. Separate Storage is met in letter, since both identifier sets sit on one Resource under distinct keys: for flattened exposition the semantic slot holds the scrape configuration and the application's identifier sits under a name no generic OTel consumer interprets. Complete Join Key When Available and default compatibility are met exactly as Option C meets them. Queryable Resource Attributes is **not met** for flattened exposition: `service.name` is absent under never-derive and holds the scrape configuration under derivation, so the application's value is queryable only as `service_name`.

The choice between C and C.1 is a value judgment, not a measurement. Underscore escaping is the Go SDK exporter's default, so the flattened path is the populous one wherever that exporter is used: C.1 leaves Practical Issue 3 unfixed there, while C fixes the pollution for that same population by interpreting the flattened value as a covered mapping input, which is exactly what moves the label. What remains unmeasurable either way is how often an attribute is literally named `service_name`, which no wire form reveals.

### Rollout

The producer reserved-pair control, consumer reserved-pair semantics gate, entity-aware consumer synthesis, producer EntityRef emission, and never-derive setting are separate capabilities. New controls default to disabled. Roll out in this order:

1. Deploy consumer versions that implement the reserved-pair semantics gate.
2. Audit existing Resource traffic for complete or partial reserved pairs and for attributes that encode to the reserved `target_info` output names.
3. Enable consumer semantics, including one-shot output-pair resolution, atomic recognition, fallback, encoded-name reservation, and collision-safe descriptive exposure. A stateful consumer requires a positive finite `R` that covers every accumulated value's inactivity-retention interval; otherwise it uses stateless-safe descriptive suppression. Stateful proof stays suppressed through exactly `R` unless a continuity-qualified restore completes with eligible untainted state; a restored taint remains authoritative. Current Collector consumers have no such restore path and always warm after process restart. Warm-up and the expected all-missing state before producer emission are silent; persistent anomalies use transition-bounded proof-state diagnostics rather than one warning per exposition.
4. Deploy and explicitly activate entity-aware consumer synthesis where planned EntityRefs may arrive. Audit every intermediary for preservation of both Resource attributes and `Resource.entity_refs`; dropping either is a semantic downgrade. Activation can re-key existing entity-bearing payloads, so stage it independently after reserved-pair semantics. Referenced attributes always follow the identifying path; keeping the reserved-pair gate enabled additionally provides collision-safe handling for an unreferenced pair in its non-identifying provenance role.
5. Enable producer reserved-pair emission and, for Option C rather than C.1, covered-name recovery. A push producer remains request-local unless a positive `H` is configured with refresh and delivery bounds that satisfy the association contract. Cross-request mode stays tainted through exactly `H` unless a continuity-qualified restore supplies eligible untainted state; a restored taint remains authoritative. Current Collector receivers have no such restore path. During warm-up it suppresses association-derived Resource metadata without suppressing ordinary translated output, and recovery may re-key Resources and downstream series. Capacity loss, including during restore catch-up, restarts that scope-wide interval.
6. Enable producer EntityRef emission only after every required consumer is entity-aware and the intermediary audit is clean. Relay only through a standardized mechanism that can preserve the complete logical source declaration. A present declaration that cannot be relayed losslessly blocks that entity-emitting translation rather than becoming inference input; only a source with no declaration may use schema-pinned inference, with `schema_url` populated when the selected schema defines one. Before standardization, pair-only scrape-target emission requires separately enabled matching pinned producer and consumer profiles plus an explicit isolation guarantee and must not cross that deployment boundary. Once the final context-inclusive semantic convention exists, disable pair-only emission before activating final-schema consumers; a pair-only declaration is not silently upgraded or accepted as conforming. Infer the final scrape-target join EntityRef only when every identifying key it defines is reliably available; a missing domain key leaves that Resource entity-less with the reserved fallback. Migration emits a replacement identity and intentionally re-keys from the verbatim legacy or experimental synthesized pair; it never mutates an existing entity's identity in place. Keep reserved-pair emission enabled on Option C producer paths, including UUIDv5 `instance` for an emitted scrape-target entity.
7. Optionally enable never-derive last, after every required entity-unaware consumer has fallback active and every entity-aware consumer can synthesize emitted scrape-target entities while producer paths lacking their complete identifying set retain the entity-less fallback.

An old or gate-disabled consumer may carry the pair as ordinary Resource metadata, but it provides no fallback or collision-safe exposure guarantees. An entity-unaware consumer may also preserve EntityRefs yet still resolve output from the flat attributes; enabling entity synthesis later re-keys the same payload. Enabling consumer semantics can switch partial Resource-derived output to a complete reserved pair and removes ordinary `target_info` metadata that encodes to the reserved output names. Enabling producer emission can change Resource shape and, once consumer semantics are active, can reshape generated `target_info` or re-key series with a complete Resource-derived pair. Cross-request producer association adds another transition at recovery from startup or state loss; operators must allow for temporary scrape-derived or covered-absent state during warm-up. Persisted state alone does not remove either startup interval: only a state checkpoint atomically coupled to durable source positions and replay, or a fenced no-gap handoff, does. Enabling never-derive can make a Resource service-less and relies on the entity-less fallback or the scrape-target entity. Defaults remain compatible only while the relevant new controls are disabled; any future default flip is a separate compatibility decision.

Transparent intermediaries need no changes when they preserve Resource attributes and EntityRefs together. Processors that drop, rename, promote, or merge attributes, discard EntityRefs, or change a referenced attribute without updating its declaration are not transparent and must be audited. Re-exposure through a pull exporter and re-scraping behave as federation does today; `honor_labels: true` on the downstream scraper preserves whatever output identity labels the exporter emitted, but flat exposition cannot by itself preserve the EntityRef declaration.

Standardization needs: register `prometheus.job` and `prometheus.instance` in semantic conventions and amend the compatibility specification to define their provenance, producer emission, per-series Remote Write applicability when the pair is incomplete, complete-source pair resolution, exact association and Consumer series keys, observation selection, strict cross-request association and retention-covering proof horizons, association- and proof-diagnostic cadence, atomic consumer semantics, encoded-output-name ownership, role-aware bounded contributor proof and recovery, fail-closed proof overflow, cursor-coupled checkpoints and fenced handoff, catch-up output behavior, never-derive behavior, and the bounded covered-name interpretation. The entity-era specification additionally needs the intended upcoming Entity data model semantics under which Resource identity is exactly the union of the Resource key/value pairs referenced through all of that Resource's EntityRefs' `id_keys`; the final scrape-target entity type; its Prometheus metadata join semantics; the label-space domain within which that join identity is unique; and one fixed complete identifying set for that entity type. The pair-only form is only a structurally encodable pre-standardization experiment whose pinned profile and hidden isolation boundary are not interoperable through EntityRef. The final interoperable semantic convention needs a minimally sufficient context-inclusive set of stable, repeatable domain attributes, with every such Resource key referenced through `id_keys`. Producers follow their pinned schema and do not vary that set from downstream topology; `schema_url` and mapping version describe interpretation rather than an entity instance's domain. The Prometheus mapper consumes the exact referenced union in its input without implicit schema conversion; Entity type, schema URL, roles, and set membership remain independently relevant to validation, relay, and merge compatibility. It also needs a lossless EntityRef relay format and its missing-attribute, reserved-key collision, and rebinding rules; schema-pinned inference rules; the exact `job` rule; UUIDv5 namespace, canonical ordering, attribute key/value type framing, and Prometheus mapping versioning; identifying-attribute query placement; and mixed-version behavior. Until those details are standardized, `prometheus.scrape_target`, EntityRef relay, and the concrete synthesis examples here are working design names and planned behavior, not an interoperable wire contract.

### Arve Knudsen: Option C, with Variant C.1 as fallback

Preferred: Option C — a valid EntityRef set governs planned entity-aware synthesis; otherwise a complete legacy Resource-derived pair has precedence, with `prometheus.job` and `prometheus.instance` as non-identifying scrape provenance and the whole-pair fallback when legacy Resource translation is incomplete. That provenance role does not make the pair a formal Entity description unless a source EntityRef names it in `description_keys`. With no source EntityRef declaration, the entity-era counterpart of that fallback is a sole scrape-target join entity carrying every identifying key required by its final schema; where complete application identity is reliable, the producer may instead infer the application EntityRef set selected by its pinned schema. Before standardization, the pair-only form is only a structurally encodable experiment requiring matching pinned producer and consumer profiles plus an explicit isolation guarantee; outside that profile, a producer lacking the context required by the final scrape-target semantic convention remains entity-less and preserves the whole-pair fallback. Acceptable fallback: Variant C.1, if lossy covered-name recognition on `target_info` is rejected; precedence matters more than recognition, and C.1 keeps the same behavior for unambiguously mapped covered attributes.

Reasoning:

* **Three roles must stay distinct.** The normalized scrape pair records Prometheus's final target coordinates after scrape processing. Under the intended upcoming Entity data model semantics for Resource identity assumed by Option C, identity is exactly the union of Resource key/value pairs referenced through `id_keys` across all of that Resource's entities; this is a required standardization outcome, not a claim about current published Development Resource semantics. Without EntityRefs, the published Prometheus mapping treats the covered service triplet as identifying. Output Prometheus `job` and `instance` are the target-disambiguation and metadata join key; under the planned entity mapping they are synthesized from the identifying union, while the entity-less mapping uses the covered triplet and then Option C's complete reserved fallback. Option C attaches the normalized pair as reserved provenance to every eligible emitted OTLP Resource produced from ordinary series; valid Remote Write series without a complete pair remain on the legacy path. It projects accepted target metadata only while association completeness is proved; a target-info-only unit can update association state without emitting a Resource. During fail-closed recovery it deliberately withholds unproved association-derived metadata. Flat attributes and recovered aliases can feed the current covered mapping and, without entities, the legacy identifying subset, but prove neither application authorship nor an entity declaration.
* **Separate storage does not settle projection precedence.** On entity-less input where both a complete legacy Resource-derived output pair and a reserved scrape pair exist, B and C retain their underlying attributes on the Resource. B gives the reserved scrape pair authoritative output precedence, displacing the pair produced by the existing Resource mapping. C keeps the complete legacy pair authoritative and uses the reserved pair only as a whole-pair fallback; it never mixes the two sources. With a valid EntityRef set, C instead lets the exact entity-declared identifying union govern synthesis. This is an explicit tradeoff: C preserves continuity with the applicable Resource mapping, but re-keys Prometheus series away from their source scrape coordinates whenever the legacy covered mapping or entity synthesis wins.
* **The join must not advertise a false origin.** When several Resources converge on one output pair, `target_info` cannot carry one contributor's scrape coordinates as though they described all contributors. Every active contributor must use a Resource-derived output pair and carry the same complete descriptive pair; an entity-identifying or fallback contributor suppresses provenance even when its pair bytes agree. Otherwise both provenance labels are suppressed.
* **Scrape provenance should not outrank the applicable Resource-derived identity.** When Entity-declared identity or the complete legacy covered mapping supplies the applicable pair, merely storing or renaming reserved scrape provenance does not override it. This precedence rule does not make every default deployment monitoring-independent: while default derivation remains enabled, missing covered attributes can still be synthesized from scrape coordinates and thereby determine the entity-less legacy identifying triplet. Avoiding that path requires `never-derive` or a separately reliable application EntityRef declaration or inference; a scrape-target EntityRef is not inferred from default-derived covered values. Option C's lossy recovery can instead interpret flattened application-looking values into the legacy triplet, but that remains an explicit compatibility policy rather than proof of application authorship. Where the legacy mapping remains incomplete, the stored pair is the best complete operational join available rather than a claim that it was application-authored. On that entity-less path, partial covered values remain members of the legacy mapping-specific identifying subset but do not combine with the reserved values in the resolved output pair. In the entity era the fallback case becomes a sole scrape-target join entity only when its complete convention-defined identity is reliable; otherwise it stays entity-less. When that entity is emitted, covered values not referenced by any EntityRef remain unreferenced, non-identifying Resource metadata and become formal Entity descriptions only if named in `description_keys`.
* **Covered-name recovery is a bounded compatibility choice.** C is preferred over C.1 because it restores the registered covered attributes for the common flattened Go SDK `target_info` path, keeping the covered mapping aligned between scraped and directly pushed telemetry when the application values survive. Recognition is limited to `target_info` and the three covered names: equal aliases collapse, while conflicting forms omit only the affected covered attribute with a bounded diagnostic. If that lossy interpretation is rejected, C.1 retains the same projection precedence and whole-pair fallback without covered-name recovery.
* **Compatibility requires ordered activation.** Reserved-pair emission, reserved-pair consumer semantics, entity-aware synthesis, producer EntityRef emission, and never-derive are separate controls. Old consumers can transport the attributes and EntityRefs yet still provide neither fallback, collision guarantees, nor entity synthesis; implementations that group by the complete Resource attribute set may also regroup the augmented payload. Reserved-pair semantics therefore deploy and activate first, then entity-aware consumers and EntityRef-preserving intermediaries, then producer EntityRef emission, with never-derive last.
* **Current query behavior is evidence, not a permanent law.** PromQL `info()` and classic joins make `job` and `instance` operationally important today. When translating a Resource to Prometheus, the design synthesizes a complete pair from a valid EntityRef set when entity-aware mapping is active; otherwise it emits a complete pair whenever the legacy Resource mapping or reserved provenance supplies one whole source. It avoids claiming that today's `info()` implementation constrains every future metadata model.
* **Entity compatibility should be designed in, with planned details labeled honestly.** The entity model and `entity_refs` are Development, and the concrete Prometheus mapping is planned rather than published. The direction is nevertheless material: under the intended upcoming Entity data model semantics for Resource identity assumed here, all of a Resource's EntityRefs contribute one identifying union, and planned ingestion derives a UUIDv5 `instance` from the exact referenced key/value union presented to the mapper. Entity type, `schema_url`, key roles, and EntityRef decomposition do not enter that UUID input, and the mapper performs no implicit schema conversion. Equal synthesis input does not make differently typed, versioned, or decomposed declarations merge- or relay-equivalent; those fields remain Entity compatibility state, while an upstream schema conversion that updates attributes and references together can change the union and re-key output. Option C composes without a pair-first carve-out: losslessly relay a valid source declaration through a future standardized mechanism; only when no source declaration is present, infer the complete application EntityRef set selected by a pinned schema from reliable identifying values or, when the entity-less resolver would consume the reserved fallback, declare the sole working-name `prometheus.scrape_target` entity with its complete reliable identifying set. That entity denotes the Prometheus metadata join identity within a label-space domain, not the underlying application or a complete configured scrape loop. Its final semantic convention fixes one minimally sufficient, stable, repeatable identifying set. The pair-only form is only a structurally encodable pre-standardization experiment requiring matching pinned producer and consumer profiles plus an explicit isolation guarantee; it is not a conforming instance of the final convention and must not escape that deployment. This is not a per-Resource or downstream-topology choice, and neither `schema_url` nor mapping version supplies the missing domain identity. The producer does not infer application and scrape-target roles together or mask application identity with scrape coordinates, but it preserves a valid source-authored combination and its intentional union. A present malformed or non-relayable declaration is not absence and cannot trigger inference or legacy fallback. Exact `job`, UUID canonicalization and mapping version, entity registration and domain semantics, relay and conflict rules, and identifying-value placement remain standardization work, so the document uses symbolic outputs where those choices matter.

Conceded: The Resource-pair-first shift changes output `job` for targets whose exposition exposes a complete covered mapping, including the common flattened path when Option C's lossy recovery is enabled. An incomplete covered mapping instead falls back to the complete scrape pair, so monitoring configuration still determines the operational join for that entity-less class. Entity-aware activation causes an intentional re-key: even a scrape-target join entity receives the synthesized UUIDv5 `instance` rather than its original scrape `instance`. Any later change across successive Resources that changes the exact identifying union — for example, an EntityRef begins or ceases to contribute a referenced key, an associated entity is replaced as its lifecycle changes, or an upstream schema conversion rewrites referenced keys and values — produces another synthesized identity and output pair. An identifying value does not mutate within one entity's lifetime; a different value represents a different or replacement entity, while an in-place mutation violates the Entity contract. A synthesis or mapping-version change may also re-key an unchanged logical union. Migration from the experimental pair-only profile to the final context-inclusive entity likewise emits a replacement identity and re-keys; it never mutates the experimental entity in place. Old and new series can overlap until stale retirement, and Resource-first or Entity-derived resolution can make distinct scrape-origin streams converge on one output pair. Different valid EntityRef declarations, including declarations with different types, decompositions, or schema versions, converge on the same synthesized `instance` when their exact referenced unions match even though they need not be merge- or relay-equivalent; whether they converge on the complete pair also depends on the planned `job` rule. Identical metric series may then become duplicate writers or collide in an existing accumulator. The contributor proof and provenance suppression prevent one origin from being advertised as common `target_info` metadata, but they do not deduplicate samples or provide exactly-once delivery. These migration and convergence costs are real. The experimental pair-only scrape-target form also cannot safely represent independent Prometheus label spaces in a pipeline that combines them because its isolation boundary is not carried in EntityRef; the interoperable definition avoids that collision by fixing minimally sufficient, stable, repeatable domain attributes in `id_keys` and the identifying union. Option C intentionally prioritizes Resource-path continuity and separation of application identity from scrape provenance over preserving every source scrape stream. Variant C.1 exists if the group decides the ambiguity of underscore recovery or the size of the affected population is decisive; it changes which entities can be inferred but does not avoid entity synthesis once an EntityRef is present.
